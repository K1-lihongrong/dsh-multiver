## GAP-001：dsh 首次（冷）启动超时导致"首次失败、再点成功"

- **现象**：点击「运行」某版本，首次可能失败（界面无提示或报启动超时），**再点一次就正常**。用户报告"无法复现"。
- **状态**：🟢 已闭环（已止血 + 根因已定位，见下）
- **首次复现证据**（阶段一日志系统上线后立即捕获，2026-10-02）：
  - 第 1 次启动（冷）：`logs/session-20261002-073420-*.log` **完全空白**（无任何 stdout/stderr），
    `logs/app.log` 记录 `[launch_window] 0.1.7-rc.2 (启动超时：30 秒内未解析到 dsh web 地址)`
  - 手动直接运行 `node_modules/.bin/dsh web --port 0 --no-open`：**立即输出 URL**，成功
  - 第 2 次启动（热）：`session-20261002-073730-*.log` 正常 `[out] dsh web: http://127.0.0.1:...`，成功
  - → **"第一次失败、第二次成功"完整复现**
- **假说**：dsh 冷启动耗时超过原 30 秒硬超时。dsh 启动期间**不打印任何输出**（静默加载，
  最后才输出 URL），故超时前 session 日志一片空白。
- **已做（止血，阶段一）**：
  - `launcher.rs` 启动超时 30s → **90s**（`LAUNCH_TIMEOUT_SECS`）
  - 超时错误文案改进，提示"首次启动较慢可重试、反复超时看会话日志"
- **根因调查结果**（2026-10-02，WSL Debian 13 + Windows 实测）：
  - dsh 规模：**约 26000 个文件 / 450~500 MB**（node_modules）
  - 实测启动耗时（输出 URL 的墙钟时间）：

    | 环境 | 冷启动 | 热启动 |
    | :--- | :--- | :--- |
    | Linux（drop caches 后） | **2.4 s** | 1.4 s |
    | Windows 0.1.7（已跑过） | — | **3~4 s** |
    | Windows 0.2.0-rc.2（首次） | — | **10.6 s** |

  - **结论**：在受控测量下，dsh 启动耗时 **2~11 s，均远低于 30 s**，无法在实验环境复现 >30s。
  - 因此原失败**不是 dsh 固有属性**，而是**首次运行时的偶发环境因素**（最可能：Windows Defender
    实时保护首次逐个扫描这 26000 个文件 + 磁盘/CPU 并发负载，使实际耗时被放大到超过 30s）。
    这与"再点就成功"（文件已被扫描、进入缓存）的现象一致。
- **处置决定**：
  - ✅ 保留 **90s 超时**（止血）——首次偶发慢时不再误判失败
  - ✅ 根因归类为"首次运行的杀软/磁盘偶发"，**不再进一步优化**（收益低）
  - 可选（未做，见文末"已知未做项"）：在错误提示中建议将数据目录加入杀软排除项
- **优先级**：低（已闭环）
- **关联**：阶段一（可观测性）的直接收益案例——此 bug 过去无痕，加日志后一次复现即捕获。

## GAP-003：`lib.rs` 单文件过大（>900 行）

- **现象**：命令层、窗口生命周期、注入脚本、日志 helper 等混杂于 `lib.rs`。
- **状态**：🟢 已完成（选项 A + B）
- **选项 A（结构抽取）**：
  - 窗口/平台辅助 → `window.rs`；日志便捷函数 → `logging.rs`；`lib.rs` 971 → 892
- **选项 B（命令层拆分）**：
  - 前置：先给命令层提取并补齐纯逻辑测试（`build_topbar_script`/`resolve_home`/
    `Config::apply_install_result`/`remove_version_refs`/`Dirs::resolve`），测试 41 → 57
  - 命令层 → 新建 `commands.rs`（738 行）；`lib.rs` → **190 行**（仅模块声明/共享类型/`run()`）
  - 纯移动，无逻辑改动；Windows 57 / Linux 53 测试通过，两平台 0 警告
- **集成测试评估（A 项）**：❌ 不做（见文末"已知未做项"）。原因：命令层已薄化 + 纯逻辑已提取单测覆盖，
  其自身无"未被测试的独立逻辑"；而 Tauri 集成测试环境依赖重（WebView/xvfb）、
  命令内 `manager_dir_plain()` 读 `current_exe()` 难以注入临时路径、破坏性命令难测——
  投入产出比低。若未来命令层出现复杂编排逻辑或只有集成测试能发现的 bug，再重新评估。
- **优先级**：低（已完成）

  - **测试**：`cargo test --lib` **37 passed, 0 failed**（Windows 为 41；差 4 个是 actions 转发脚本测试，限定 cfg(windows)）
  - **运行时**（2026-10-02 补充）：

## GAP-008：WSLg 下内嵌窗口显示「重新连接中」，目录选择器报 Load failed

- **现象**（2026-10-03，WSLg + Debian 13 + WebKitGTK 2.54）：
  - 内嵌 dsh 窗口能加载页面（logo/侧栏/设置可见），但右下角常驻「重新连接中…」
  - 打开「选择工作区目录」报 `client api: directoryPicker/list failed: Load failed`
  - **浏览器打开正常**（同一 dsh server，用系统浏览器访问同一 URL）
- **调查过程（已排除的层）**：
  - **网络层正常**：tcpdump 抓包显示 71~320 个 `POST /api/...` **全部 200 OK**，无错误状态码、无 RST
  - **认证正常**：WebView 请求带了正确的 `dsh-auth-*` Cookie；curl 完整 token→cookie→API 流程均 200
  - **RPC 正常**：手动 `POST /api/directoryPicker/list` 返回 200（业务层错误，非网络/认证错误）
  - **server 正常**：会话日志有 URL、端口 LISTEN、`store prune` 等后端行为均正常
  - **进程正常**：dsh server 稳定存活（此前"进程反复起死"系黑匣子误报——`pgrep` 匹配到了 dsh 启动 shell wrapper 的临时子进程）
- **定位**：
  - 报错字符串来自 dsh 前端（`dsh-client-ui-settings-general` 的 `connection.connecting`、
    `dsh-client-ui-settings-models` 的 `welcomeError`），**非管理器代码**
  - 关键证据：抓包里 **`workspaceFiles/list` 能发（320 次），但 `directoryPicker/list` 一次都没发出**
    → `Load failed` 是 **WebKit 的 fetch 错误**，请求在发出前即失败
  - 疑为 **dsh 前端某 API（fetch 变体 / Worker / 流式读取）在 WebKitGTK 下不可用**，
    而 Chromium/系统浏览器支持
- **性质判断**：
  - **非管理器 bug**（管理器只负责"启动 dsh + 用 WebView 显示"）
  - **WSLg 环境特有**（WSLg 的 Weston + WebKitGTK 组合特殊）；真 Linux 桌面（GNOME/KDE）**待验证**
  - 功能基本可用（页面能加载、能交互），主要是**连接状态显示异常 + 目录选择器不可用**
- **状态**：🔴 未解决（已定位到 dsh 前端 + WebKitGTK 兼容层，超出管理器可控范围）
- **建议**：
  - 在**真 Linux 桌面**验证是否复现（若不复现，则确认为 WSLg 特有问题，无需处理）
  - 受影响用户可改用管理器的「**浏览器打开**」功能（该系统浏览器路径正常）
- **优先级**：低（WSLg 专属、功能基本可用、非管理器可控）

## GAP-009：前端 `App.vue` 单文件过大（>1300 行）

- **现象**：`src/App.vue` 承载了全部 UI —— 已安装/可用版本列表、环境自检、路径设置、数据隔离、
  维护面板、换源重试弹窗、批量操作、版本更新说明等，单文件已达 1300+ 行。
- **状态**：🟡 进行中（已拆 1 步；完整分步计划见 [App 拆分计划](App拆分计划.md)）
- **进展**：第 1 步已抽出 `NotesPanel.vue`（App.vue 1336 → 1133 行，提交 e4ab3c5）
- **建议动作**：按 [App 拆分计划](App拆分计划.md) **分步实施**（每步拆一个组件，拆完手动验证）。
- **为什么暂缓**：
  - 纯结构优化，**无功能收益**；Vue SFC 单文件 1300 行虽偏大但可维护
  - 拆分需要大量机械移动 + 组件间状态/事件串联，**风险与工作量都不小**（且前端无自动化测试兜底）
  - 与"外科手术式修改"原则一致：等**真正要密集改前端**时再拆，避免为拆而拆
- **重新考虑的条件**：前端改动开始密集、或单文件大到明显影响开发效率时。
- **优先级**：低
