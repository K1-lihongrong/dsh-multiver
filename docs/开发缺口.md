## GAP-001：dsh 首次（冷）启动超时导致"首次失败、再点成功"

- **现象**：点击「运行」某版本，首次可能失败（界面无提示或报启动超时），**再点一次就正常**。用户报告"无法复现"。
- **状态**：🟢 已闭环（已止血 + 根因已定位，见下）
- **首次复现证据**（阶段一日志系统上线后立即捕获，2026-10-02）：
  - 第 1 次启动（冷）：`logs/session-20261002-073420-*.log` **完全空白**（无任何 stdout/stderr），
    `logs/app.log` 记录 `[launch_window] 0.1.7-rc.2 (启动超时：30 秒内未解析到 dsh web 地址)`
  - 手动直接运行 `node_modules/.bin/dsh web --port 0 --no-open`：**立即输出 URL**，成功
  - 第 2 次启动（热）：`session-20261002-073730-*.log` 正常 `[out] dsh web: http://127.0.0.1:...`，成功
  - → **"第一次失败、第二次成功"完整复现**
- **假说**：dsh 冷启动耗时超过原 30 秒硬超时。dsh 启动期间**不打印任何输出**（静默加载，
  最后才输出 URL），故超时前 session 日志一片空白。
- **已做（止血，阶段一）**：
  - `launcher.rs` 启动超时 30s → **90s**（`LAUNCH_TIMEOUT_SECS`）
  - 超时错误文案改进，提示"首次启动较慢可重试、反复超时看会话日志"
- **根因调查结果**（2026-10-02，WSL Debian 13 + Windows 实测）：
  - dsh 规模：**约 26000 个文件 / 450~500 MB**（node_modules）
  - 实测启动耗时（输出 URL 的墙钟时间）：

    | 环境 | 冷启动 | 热启动 |
    | :--- | :--- | :--- |
    | Linux（drop caches 后） | **2.4 s** | 1.4 s |
    | Windows 0.1.7（已跑过） | — | **3~4 s** |
    | Windows 0.2.0-rc.2（首次） | — | **10.6 s** |

  - **结论**：在受控测量下，dsh 启动耗时 **2~11 s，均远低于 30 s**，无法在实验环境复现 >30s。
  - 因此原失败**不是 dsh 固有属性**，而是**首次运行时的偶发环境因素**（最可能：Windows Defender
    实时保护首次逐个扫描这 26000 个文件 + 磁盘/CPU 并发负载，使实际耗时被放大到超过 30s）。
    这与"再点就成功"（文件已被扫描、进入缓存）的现象一致。
- **处置决定**：
  - ✅ 保留 **90s 超时**（止血）——首次偶发慢时不再误判失败
  - ✅ 根因归类为"首次运行的杀软/磁盘偶发"，**不再进一步优化**（收益低）
  - 可选（未做，视需要）：在错误提示中建议将数据目录加入杀软排除项
- **状态**：🟢 已止血 + 根因已定位（首次运行的杀软/磁盘偶发，非 dsh 固有慢）
- **优先级**：低（已闭环）
- **关联**：阶段一（可观测性）的直接收益案例——此 bug 过去无痕，加日志后一次复现即捕获。

## GAP-002：`build_topbar_script` 内联 100+ 行 JS 字符串

- **现象**：`lib.rs` 用 Rust 字符串手工拼接注入到 dsh 页面的 JS（顶部小栏），
  无语法高亮/补全/报错，转义繁琐，且随功能持续增长。
- **状态**：🟢 已完成（v0.2.0，提交 ff7cd3d）
- **做法**：外置为 `src-tauri/src/topbar.js`，`build_topbar_script` 用 `include_str!` + 占位符替换。
- **优先级**：低

## GAP-005：Unix 进程管理分支尚未真机验证

- **现象**：阶段四将 `jobobj.rs` 抽象为跨平台进程守卫（Windows Job Object / Unix 进程组+PDEATHSIG），
  但开发环境是 Windows，`#[cfg(unix)]` 分支**不参与编译**，仅经逻辑推演，未在真 Linux 上跑过。
- **状态**：🟢 已闭环（编译 + 测试 + 运行时 全部验证，2026-10-02）
- **验证记录**（WSL2 Debian 13 / rustc 1.99.0 / WSLg）：
  - **编译**：`cargo check` Linux 上 **0 error / 0 warning**
  - **测试**：`cargo test --lib` **37 passed, 0 failed**（Windows 为 41；差 4 个是 actions 转发脚本测试，限定 cfg(windows)）
  - **运行时**（2026-10-02 补充）：
    - GUI：`pnpm tauri dev` 在 WSLg 下**成功启动窗口**，无崩溃
    - CLI：`--help`/`--list`/`--set-default`/`--uninstall` 均正常
    - 转发脚本：`--set-default` → 在 `~/.local/bin/dsh` 生成正确 `#!/bin/sh` 脚本（权限 0755）；`--uninstall` 后**正确删除**
    - **进程管理运行时验证**（独立最小程序，模拟管理器/子进程/孙进程）：
      - **PDEATHSIG**（管理器被 `kill -9` 强杀）：子进程被内核**自动清理**，无孤儿
      - **进程组 + killpg**（正常关窗路径）：`kill -9 -<pgid>` **整棵进程树（含孙进程）被清理**，
        且父进程不受波及
    - → 验证了 `path_bin_dir` / `build_forward_script` / `write_forward_script` / 删除分支的**运行时行为**
- **涉及**：`jobobj.rs` 的 `configure_command`/`attach`（Unix）、`launcher.rs` `kill_tree` 的 `killpg` 分支、
  `Cargo.toml` 新增的 `[target.'cfg(unix)'.dependencies] libc`。
- **完成**（2026-10-02，WSL Debian 13 + WSLg）：编译 0 警告、37 测试通过、GUI 启动、
  CLI 正常、转发脚本生成/删除正确、PDEATHSIG + killpg 进程清理运行时验证通过。
- **优先级**：低（已闭环）
- **关联**：`docs/Linux适配开发计划.md` 阶段 4。
