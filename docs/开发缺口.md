## GAP-001：dsh 首次（冷）启动超时导致"首次失败、再点成功"

- **现象**：点击「运行」某版本，首次可能失败（界面无提示或报启动超时），**再点一次就正常**。用户报告"无法复现"。
- **状态**：🟢 已闭环（已止血 + 根因已定位，见下）
- **首次复现证据**（阶段一日志系统上线后立即捕获，2026-10-02）：
  - 第 1 次启动（冷）：`logs/session-20261002-073420-*.log` **完全空白**（无任何 stdout/stderr），
    `logs/app.log` 记录 `[launch_window] 0.1.7-rc.2 (启动超时：30 秒内未解析到 dsh web 地址)`
  - 手动直接运行 `node_modules/.bin/dsh web --port 0 --no-open`：**立即输出 URL**，成功
  - 第 2 次启动（热）：`session-20261002-073730-*.log` 正常 `[out] dsh web: http://127.0.0.1:...`，成功
  - → **"第一次失败、第二次成功"完整复现**
- **假说**：dsh 冷启动耗时超过原 30 秒硬超时。dsh 启动期间**不打印任何输出**（静默加载，
  最后才输出 URL），故超时前 session 日志一片空白。
- **已做（止血，阶段一）**：
  - `launcher.rs` 启动超时 30s → **90s**（`LAUNCH_TIMEOUT_SECS`）
  - 超时错误文案改进，提示"首次启动较慢可重试、反复超时看会话日志"
- **根因调查结果**（2026-10-02，WSL Debian 13 + Windows 实测）：
  - dsh 规模：**约 26000 个文件 / 450~500 MB**（node_modules）
  - 实测启动耗时（输出 URL 的墙钟时间）：

    | 环境 | 冷启动 | 热启动 |
    | :--- | :--- | :--- |
    | Linux（drop caches 后） | **2.4 s** | 1.4 s |
    | Windows 0.1.7（已跑过） | — | **3~4 s** |
    | Windows 0.2.0-rc.2（首次） | — | **10.6 s** |

  - **结论**：在受控测量下，dsh 启动耗时 **2~11 s，均远低于 30 s**，无法在实验环境复现 >30s。
  - 因此原失败**不是 dsh 固有属性**，而是**首次运行时的偶发环境因素**（最可能：Windows Defender
    实时保护首次逐个扫描这 26000 个文件 + 磁盘/CPU 并发负载，使实际耗时被放大到超过 30s）。
    这与"再点就成功"（文件已被扫描、进入缓存）的现象一致。
- **处置决定**：
  - ✅ 保留 **90s 超时**（止血）——首次偶发慢时不再误判失败
  - ✅ 根因归类为"首次运行的杀软/磁盘偶发"，**不再进一步优化**（收益低）
  - 可选（未做，见文末"已知未做项"）：在错误提示中建议将数据目录加入杀软排除项
- **优先级**：低（已闭环）
- **关联**：阶段一（可观测性）的直接收益案例——此 bug 过去无痕，加日志后一次复现即捕获。

## GAP-008 附录：根因修正与修复详情（2026-10-08）

**原判断错误**："dsh 前端 + WebKitGTK 兼容层"的定位是**错的**。
真正根因是 **管理器的 `jobobj.rs` 在 Unix 侧设置了 `PR_SET_PDEATHSIG=SIGKILL`**。

### 证据链（普通 X11 / Xvfb 下复现，非 WSLg 专属）

| 实验 | 结果 |
| :--- | :--- |
| 手动跑 dsh（无管理器） | ✅ 稳定存活 |
| 手动 dsh + 独立 WebKitGTK 客户端加载页面 | ✅ 稳定存活 |
| 管理器「运行」→ 内嵌窗口 | ❌ 4/4 次 dsh server 都在窗口加载后死亡 |
| cgroup OOM 记录 | 无（排除内存被杀） |
| strace 管理器 | dsh 被 **SIGKILL** 但**无任何 kill() 调用** → 内核行为 |
| **决定性实验**（最小 Rust 复刻） | spawn 线程一退出，带 PDEATHSIG 的子进程立即被 SIGKILL（wait status 9） |

### 机理

`PR_SET_PDEATHSIG` 绑定的是**发起 `spawn()` 的那个线程**，不是进程。
本项目的 spawn 发生在 `tauri::async_runtime::spawn_blocking` 的**线程池线程**上——
命令返回后线程被回收，内核随即按 PDEATHSIG 杀掉 dsh。时间线完全吻合：
URL 输出 → 窗口打开、页面加载成功 → command 返回、池线程回收 → dsh 被 SIGKILL →
前端所有 API 失败 →「重新连接中」。

**为什么 Windows 没有**：Windows 用 Job Object（`KILL_ON_JOB_CLOSE`），不依赖 PDEATHSIG。

### 修复（v0.2.4）

- **`jobobj.rs`**：Unix 侧**移除 `PR_SET_PDEATHSIG`**，只保留 `process_group(0)`（供 killpg）
- **`procreg.rs`（新增）**：残留进程登记 + 启动清理，兜底"管理器被 `kill -9`"场景
- **回归测试**：`jobobj::tests::gap008_pdeathsig_kills_child_on_thread_exit`
  （对照实验：无 PDEATHSIG → 子进程存活；有 PDEATHSIG → 子进程被杀）
- **验证**：Windows 68 / **Linux 78 测试全通过**（Debian 13）

> ⚠️ **集成验证局限**：本机 WSL 上 `dsh web` 自身无法启动（node v20 < dsh 要求的 22，
> 且 node 22 安装受阻于 apt 依赖冲突），故"真 dsh web 进程存活"的端到端验证**未完成**。
> 但单元级对照实验已直接证明根因与修复有效性。

## GAP-010：管理器被 `kill -9` 后，dsh 进程会残留到下次启动

- **现象**：Unix 侧移除 PDEATHSIG（GAP-008 的修复）后，若管理器被 `kill -9` 或崩溃，
  来不及跑清理代码，dsh 进程（及其 node 子树）会**残留**，直到下次启动管理器。
- **状态**：🟢 已缓解（v0.2.4）—— `procreg` 登记 + 启动清理把代价降到"下次启动即清"
- **覆盖情况**：

  | 场景 | 清理方式 |
  | :--- | :--- |
  | 正常关窗 | `killpg`（进程组） |
  | 正常退出 | `killpg` |
  | **管理器被 `kill -9`** | **下次启动时 `procreg::cleanup_stale`** |

- **为什么不彻底**：要"零残留"需把 `spawn()` 放在**生命周期与进程一致**的常驻线程上
  （让 PDEATHSIG 语义正确）。评估后**暂缓**：改动涉及线程模型 + channel 通信，
  而"强杀管理器"场景极罕见（正常退出/关窗都走 killpg）。
- **重新考虑的条件**：若"强杀后残留"成为实际问题（用户反馈），再做常驻 spawner 线程。
- **优先级**：低（已缓解，代价是强杀后的一个窗口期）

## GAP-011：改过数据根目录后，旧 root 下的残留登记不会被打扫

- **现象**：`procreg` 的登记文件在**数据根目录**下（`<root>/logs/dsh-procs.json`）。
  若用户改过「数据根目录」（`set_root`），旧 root 下遗留的登记**不会被新 root 的启动清理触及**——
  旧 root 里那个 dsh 若仍存活，将**永久残留**（不再有任何机制去清它）。
- **状态**：✅ **已修复**（2026-10-08）—— `set_root` 切换前对**旧 root** 调一次 `procreg::cleanup_stale`
- **触发条件**（较窄）：
  1. 某版本开着内嵌窗口（dsh 在跑）
  2. 用户改数据根目录（`set_root`）
  3. 之后管理器被强杀（否则正常退出会注销旧 root 的登记）
  —— 三步都满足才遗留。
- **修复**：`commands.rs` 的 `set_root` 在写新配置前，对旧 root 调 `procreg::cleanup_stale`，
  并写维护日志。仅当旧 root 与管理器目录不同时才执行（避免误清管理器自身目录）。
- **优先级**：低（已修复）

## GAP-014：管理器写的 `dsh` 命令与官方 `npm i -g` 装的 dsh 同名冲突

- **现象**：用户"设为默认"时，管理器在 `%APPDATA%\npm\`（Windows）/ `~/.local/bin`（Unix）
  生成 `dsh` / `dsh.cmd` 转发脚本。**若该位置已有官方 `npm i -g @deepseek-ai/dsh` 装的同名命令**：
  - **同名文件冲突**：管理器**直接覆盖**，无检测、无提示
  - **PATH 顺序决定谁生效**：官方装到别处且 PATH 靠前 → 敲 `dsh` 走官方，管理器脚本被绕过
  - **卸载删错**：`remove_version_refs` 会删 `dsh.cmd`——若那本是官方装的，用户的官方 `dsh` **消失**
- **证据**：`commands.rs` 的 `set_default` → `regenerate_forward_script` → `path_bin_dir`
  直接 `write_forward_script`，**不检查目标是否已存在/是否官方装的**。
  `uninstall_version` 的 `remove_version_refs` 同理无脑删。
- **影响**：用户"既官方装、又用管理器"时，`dsh` 命令归属**不确定**，且可能**误删官方命令**。
- **建议动作**（下轮）：
  - 管理器生成的脚本加**标记注释**（如 `# dsh-multiver generated`），用于识别
  - `set_default` 前检查目标：若已存在且**非**管理器生成 → **提示用户**"该位置已有 dsh，将覆盖，确定吗？"
  - 卸载时**只删自己生成的**（校验标记）
- **状态**：✅ **已修复**（v0.2.8）
- **修复**：转发脚本加标记 `dsh-multiver-generated`；`actions::existing_foreign_dsh` 检测；
  GUI `set_default` 检测到冲突返回 `DSH_CONFLICT:` 前缀 → 前端 `ask` 确认后 `force=true` 重试；
  CLI `--set-default` 拒绝并提示 `--force`；`regenerate_forward_script` 删除时校验标记（只删自生成）。
- **优先级**：中

## P7 优化备选思路（占用扫描，v0.2.11 记录）

> **背景**：`--info` / 界面「扫描占用」需遍历版本目录（约 26000 文件）逐个 open 读硬链接数（nlink），
> 实测 **约 36s**。v0.2.11 曾尝试**并行化**，反而更慢（磁盘 IO 密集，多线程加剧寻道竞争），已回退。
> 「共享了多少」是本工具**核心价值**（省磁盘卖点），不能砍精度。
>
> 下列思路来自 v0.2.11 期间的讨论，**未实施**，供将来参考。

### 思路 A：放弃精确共享，只报总量
- 只用 `dir_size`（读目录项大小，**不 open**），展示"占用约 X"，不拆分共享/独占
- **否决**：与"共享了多少"这一核心价值冲突（用户明确需要）

### 思路 B：卷级批量接口 —— ❌ 已验证不可行
- Windows `FSCTL_GET_NTFS_FILE_RECORD` / USN Journal 批量读文件记录（含链接数）
- **验证（2026-10-14）**：该接口需**卷句柄（管理员权限）**；
  实测当前进程为 Medium Integrity（非管理员），普通应用**无法使用**。排除。

### 思路 C：内存 inode 去重 —— ❌ 已验证证伪
- 设想：遍历时读 FileId，内存统计"同 FileId 出现 >1 = 共享"
- **验证（2026-10-14）**：取 `@babel/runtime/.../applyDecs.js`（nlink=6），
  全版本目录（26678 文件）扫描，该 ino **仅出现 1 次**。
- **结论**：**共享方在版本目录之外**（store + 其它版本/modpack），版本内去重**无效**。
  （`fsutil hardlink list` 证明：该文件的 6 个链接分别在 store、3 个其它版本、1 个 modpack、本版本）
- 附带：Windows 上拿 FileId 仍需 open（`FindFirstFile` 不给 FileId）

### 思路 D：遍历 store 而非版本目录 —— ❌ 已验证证伪
- 设想：遍历 store（共享的唯一真相源）替代遍历版本目录
- **验证（2026-10-14）**：store 有 **45805 个文件**（比单版本的 26678 还多），
  遍历需 **约 20s**——**不比现状快**。且"哪些被该版本引用"仍需看版本目录。排除。

### 思路 E：按"包"判定（粒度升级）—— ❌ 已验证不成立
- **假设**：pnpm 硬链接是"整包"的，一个包只需查一个文件
- **验证（2026-10-14）**：`@babel/runtime@7.29.7` 包内所有文件 nlink 一致（都是 6）✅；
  但 `@aws-sdk/core@3.978.1` 包内 nlink **不一致**（`{1:9, 6:312, 11:27, 16:15}`）❌
- **结论**：**假设不成立**——同包内文件可因被其他包引用而有不同 nlink。
  （副产物：nlink 值分布很简单，说明共享是"成组"发生的，但无法据此免去逐文件查询）

### 思路 F：读 pnpm 账本—— ❌ 已验证不可行
- 设想：pnpm 的元数据（`.package-map.json` / `.modules.yaml` / `.pnpm/lock.yaml` / `.pnpm-workspace-state.json`）
  或 `pnpm store status` 能提供文件级共享信息
- **验证（2026-10-14）**：上述文件**均为包级信息**（包名/版本/依赖/integrity），
  **无文件级硬链接或字节级共享数据**；`pnpm store status` 只输出"store 是否被改动"
- **结论**：pnpm **无现成账本**提供"文件级共享字节"

### 思路 G：减少每次 open 的开销 —— ❌ 已实施并证伪（2026-10-21）
- 原假设：`metadata()`（拿大小）+ `File::open` + `GetFileInformationByHandle`（拿 nlink）是**两次系统调用**，
  合并成一次 open + 一次句柄查询可省一半，预期 36s → 约 18s。
- **实施（v0.3.0 期间）**：新增 `file_stat(path) -> Option<(u64, u32)>`，一次 open + `GetFileInformationByHandle`
  同时取 `nFileSizeHigh/Low` 与 `nNumberOfLinks`，替换 `detail_from_files` 与 `dir_size_detail_with_progress`
  两处的 `metadata() + file_nlink()`。单测覆盖，结果正确。
- **实测（release 构建，同版本 0.2.0-rc.1，同机同口径）**：

  | 实现 | 耗时 | 扫描结果 |
  | :--- | :--- | :--- |
  | 旧（metadata + open） | **38.16 s** | 2.01 GB（复用 1.99 GB / 独占 29.53 MB） |
  | 新（单次 open 拿 size+nlink） | **39.13 s** | 完全一致 |

- **结论：无收益，反而略慢**。假设不成立——瓶颈是 **`File::open` 本身**（每个文件都必须做），
  而 `metadata()` 走的是文件系统元数据缓存，开销极小；合并后调用次数少了，但多做了
  `nFileSizeHigh/Low` 位运算与句柄转换，且 `File::open` 的代价没变。
- **处置**：代码已回退（不引入手写 unsafe 换 0 收益）。

### 根本原因：NTFS 硬链接上限 + 同内容可独立（2026-10-14 决定性别验证）

**发现**：文件 `JsonSettings.js`（内容 `export {};\n`，11 字节）在不同版本里状态**不同**：

| 版本 | nlink | ino |
| :--- | :--- | :--- |
| 0.2.0-rc.2 | **1**（独立副本） | 562949955199091 |
| 0.2.0-rc.1 | **1024**（上限） | 1407374885043214 |
| 0.1.5-rc.3 | 1024 | 同一 ino |
| 0.2.1-alpha.1 | 1024 | 同一 ino |

**解释**：
- NTFS 硬链接数**上限 1024**。`export {};\n` 这类极短、极常见的内容被海量包引用，
  链接数**早早触顶 1024**。
- 达到上限后，pnpm 再加引用**只能另存一份**（新 ino）——故 0.2.0-rc.2 里是 nlink=1 的独立副本。
- `fsutil hardlink list` 对该文件输出**正好 1024 条**，证实触顶。

**为何这堵死了所有"捷径"**：
- **"内容相同 → 共享"不成立**：同内容可因触顶而独立（反例已现）
- **"nlink 反映引用数"不成立**：1024 是**截断值**，真实引用数可能上万——**信息已丢失**
- **共享状态动态、不可预测**：取决于安装顺序、store 历史、是否触顶

**根本结论**：文件级共享状态**由文件系统 inode + 链接数决定**，而链接数有上限、pnpm 会因上限另存——
**只能逐文件读 nlink 获知，无任何可推算/预存/账本的捷径**。

### 综合结论（2026-10-14 验证；2026-10-21 补 G 的实测结论）

**已验证并证伪**：A（与核心价值冲突）、B（需管理员权限）、C（版本内 inode 不重复）、
D（store 比版本还大）、E（包内 nlink 不一致）、F（pnpm 无文件级账本）、
**G（合并 open 调用，实测 39.13s vs 旧 38.16s，无收益）**。

**结果缓存**（未列入 A~G）：✅ **已在 v0.2.13 实现**（`sizecache.rs`）。
扫描结果缓存在 `<root>/cache/size-cache.json`，以「版本目录 mtime + store mtime」为失效条件；
首次仍需全量扫描（约 38s），**后续查看直接读缓存（毫秒级）**。

**P7 现状**：A~G 全部验证完毕（A~G 均不可行或已实施），缓存方案已落地。
**剩余优化空间为零**——除非文件系统提供免 open 的批量 nlink 接口（需管理员权限，已排除）。

**本质结论**：P7 的首次扫描（实测 38s）是**算法 + 文件系统固有成本**——「精确到字节的文件级共享」必须逐文件 open 读 nlink。
根本原因（见上「NTFS 硬链接上限」）：**共享状态由 inode + 链接数决定，链接数有 1024 上限、pnpm 会因上限另存**，
故**同内容可能独立、nlink 可能被截断**——**任何"预存/推算/账本"的捷径都不成立**。
Windows 下无免 open 的批量接口（除非管理员权限）。**降不了数量级，只能缓存或小幅优化**。
