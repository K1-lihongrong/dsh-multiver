## GAP-001：dsh 首次（冷）启动超时导致"首次失败、再点成功"

- **现象**：点击「运行」某版本，首次可能失败（界面无提示或报启动超时），**再点一次就正常**。用户报告"无法复现"。
- **状态**：🟡 部分修复（已止血），根因待验证
- **首次复现证据**（阶段一日志系统上线后立即捕获，2026-10-02）：
  - 第 1 次启动（冷）：`logs/session-20261002-073420-*.log` **完全空白**（无任何 stdout/stderr），
    `logs/app.log` 记录 `[launch_window] 0.1.7-rc.2 (启动超时：30 秒内未解析到 dsh web 地址)`
  - 手动直接运行 `node_modules/.bin/dsh web --port 0 --no-open`：**立即输出 URL**，成功
  - 第 2 次启动（热）：`session-20261002-073730-*.log` 正常 `[out] dsh web: http://127.0.0.1:...`，成功
  - → **"第一次失败、第二次成功"完整复现**
- **假说**：dsh 冷启动耗时超过原 30 秒硬超时。dsh 启动期间**不打印任何输出**（静默加载，
  最后才输出 URL），故超时前 session 日志一片空白。冷启动慢的可能来源：
  node 加载大量模块 + 原生模块（node-pty / koffi）+ 杀软首次扫描。
- **已做（止血，阶段一）**：
  - `launcher.rs` 启动超时 30s → **90s**（`LAUNCH_TIMEOUT_SECS`）
  - 超时错误文案改进，提示"首次启动较慢可重试、反复超时看会话日志"
- **待做（B：根因验证，需重新构建 / 实验）**：
  - [ ] 精确测量 dsh 冷启动耗时（清空 node 模块缓存 / 杀软白名单后计时）
  - [ ] 确认是否可通过预热（后台提前拉起一次）消除首次超时
  - [ ] 评估：是否有"dsh 已就绪"的更早信号（而非等 URL），或分批超时策略
- **优先级**：中（已止血；根因确认后可进一步优化体验）
- **关联**：阶段一（可观测性）的直接收益案例——此 bug 过去无痕，加日志后一次复现即捕获。

## GAP-005：Unix 进程管理分支尚未真机验证

- **现象**：阶段四将 `jobobj.rs` 抽象为跨平台进程守卫（Windows Job Object / Unix 进程组+PDEATHSIG），
  但开发环境是 Windows，`#[cfg(unix)]` 分支**不参与编译**，仅经逻辑推演，未在真 Linux 上跑过。
- **状态**：🟢 编译+测试级已验证（2026-10-02，WSL Debian 13）；运行时行为待验证
- **验证记录**（WSL2 Debian 13 / rustc 1.99.0）：
  - `cargo check`：Linux 上 **0 error / 0 warning**
  - `cargo test --lib`：**37 passed, 0 failed**（Windows 为 41；差 4 个是 actions 转发脚本测试，限定 cfg(windows)）
  - → `cfg(unix)` 的进程组 / PDEATHSIG / killpg / Unix 转发脚本 / libc 依赖 **全部真实编译并通过测试**
- **涉及**：`jobobj.rs` 的 `configure_command`/`attach`（Unix）、`launcher.rs` `kill_tree` 的 `killpg` 分支、
  `Cargo.toml` 新增的 `[target.'cfg(unix)'.dependencies] libc`。
- **待做**：进入阶段三（跨平台）时，在能起 GUI 的真 Linux 上验证**运行时**行为：
  - [ ] 关窗后 dsh/node 进程无残留
  - [ ] 强杀管理器（kill -9）后进程无残留（PDEATHSIG 生效）
  - [ ] 需先装 Node/pnpm 才能 `tauri dev` 起窗口
- **优先级**：中（阶段三启动时必做）
- **关联**：`docs/Linux适配开发计划.md` 阶段 4。
