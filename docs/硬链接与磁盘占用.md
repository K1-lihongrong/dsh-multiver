# 硬链接与磁盘占用：为什么"看着没省磁盘"

> 面向用户。解释本工具"省磁盘"的原理，以及为什么 Windows 文件夹属性显示的占用**大于**真实占用。
> 关联：[使用手册 · 数据存储结构](使用手册.md#九数据存储结构)

---

## 一、一句话

多个 dsh 版本**共享同一份依赖文件**（硬链接），磁盘上**只存一份**。
但 **Windows 文件夹属性会把共享的文件重复计算**，所以显示的数字偏大——**那不代表真实磁盘消耗**。

---

## 二、省磁盘的原理

### pnpm 的内容寻址仓库（store）

每个 dsh 版本有各自的 `node_modules`，但它们依赖的包**不是各存一份**，而是：

1. 所有包文件存进 **`<数据根>/store/`**（内容寻址：按文件内容哈希命名）。
2. 各版本的 `node_modules` 里放的是**指向 store 的硬链接**。

### 硬链接是什么

**多个路径 → 同一份物理文件**（同一个 inode / 文件记录）。

- 文件内容**只占一份磁盘空间**。
- 多个版本"引用"它，磁盘上**不重复**。

例：`@babel/runtime` 被 3 个版本依赖：
- 不用硬链接：3 份，占 3×450MB。
- 用硬链接：store 里 1 份（450MB），3 个版本各放一个"链接"，**总共还是 450MB**。

---

## 三、为什么 Windows 属性"看着没省"

Windows 资源管理器的文件夹属性给出两个数字：

| 指标 | 含义 |
| :--- | :--- |
| **大小** | 按**目录项**累加的文件字节数 |
| **占用空间** | 同上，再按磁盘簇对齐 |

**关键**：它遍历目录树时，**每个目录项都算一遍**，**不区分是否指向同一份物理文件**。

所以共享的文件会被**重复计算**：

- 一份 450MB 的文件，被 3 个版本硬链接引用。
- Windows 属性：3 × 450MB = **1350MB**。
- 真实磁盘：**450MB**。

**结论**：Windows 属性 = **逻辑大小**（含重复计算），**不是**真实磁盘消耗。

---

## 四、怎么看到真实的"省了多少"

### 方法 1：本工具的「占用扫描」

界面「已安装版本」→ 每行「扫描占用」/ 顶部「扫描全部占用」。

工具逐个文件读硬链接数（`nlink`）：

- `nlink > 1` 的文件 = **与其他版本共享** → 计入「复用」，不重复计。
- 结果：`占用 X（复用 Y / 独占 Z）`

**「独占」才是该版本真正新增的磁盘占用。**

实测示例（6 个 dsh 版本）：

```
versions 逻辑总大小:  2571 MB    ← Windows 属性看到的
其中硬链接(共享):     2472 MB    ← 指向 store / 其他版本
独占(真实新增):         99 MB    ← 真正只属于这些版本
```

即 6 个版本本该占 ~2.5GB，实际独占仅 ~0.1GB。

### 方法 2：命令行（可选）

- **Linux/macOS**：`du -sh <目录>` —— `du` 默认**不重复计**同一 inode，结果接近真实。
- **Windows**：无内置等价命令（资源管理器会重复计）。

## 五、常见疑问

### Q：是不是我的磁盘真被占了 4.5GB？

不是。那是**逻辑大小**。共享文件只占一份。真实占用看工具的「独占」数字（或 `df` 看卷整体剩余）。

### Q：`store` 能删吗？

**谨慎**。各版本依赖通过硬链接指向 store，删了**所有版本都失效**（需重装）。详见[使用手册 · 哪些可以安全删除](使用手册.md#哪些可以安全删除)。

### Q：卸载一个版本后，`store` 会小吗？

不一定。卸载只删该版本的**链接**，store 里那份数据若**仍被其他版本引用**则保留。真正回收在**后台 `pnpm store prune`**（自动维护，7 天一跑）。

### Q：为什么工具算的"占用"和资源管理器不一样？

因为工具**去重**（按 inode 只算一次），资源管理器**不去重**（按目录项累加）。**工具的数字更接近真实磁盘消耗。**
