# v0.4.0-alpha.1 验收清单

> 版本：`0.4.0-alpha.1` · 分支：`feat/v0.4.0-alpha.1` · 验收包以 SHA256 为准
> 产物：`dsh-multiver.exe`（单文件便携版）
> exe SHA256：`228F043FB0EC2768BE66A310439E4CDFE8B778D52ED18CCB2129A50E38D5A4A6`
> 性质：alpha 验证版，**不创建 GitHub Release**

## 一、本轮新增

1. **插件检查更新修复**
   - `pnpm outdated` 在 hoisted profile 漏报范围内新版本时，对非官方插件逐项查询 registry latest 兜底。
   - 用 semver 比较，只报告真正的新版本；官方随附包的旧 prerelease 不会误报。
   - 已实测 `dsh-ops 0.5.1 -> 0.5.2` 可被扫描到。

2. **插件批量更新**
   - 「已安装」页检测到多个可更新插件后，出现「全部更新」按钮。
   - 逐项执行，显示 `i/N + 插件名 + 阶段`。
   - 单个插件失败只回滚该项，其余继续，最后汇总成功/失败数。

3. **失败回滚**
   - 更新事务为 `remove → add → verify`。
   - add 或校验失败时，按原 package.json 依赖 spec 重装旧版本。
   - 回滚失败时日志显示原错误、回滚错误和人工恢复线索。

4. **单插件更新也走事务**
   - 单插件「更新」不再由前端裸调 remove+add。
   - 官方随附 bundle 不显示更新按钮，也不会进入批量更新。

5. **精确版本豁免**
   - 安装失败输出含 `Plugin ... is incompatible with dsh ...` 时，界面自动解析包版本与 DSH 版本。
   - 可一键调用官方 `dsh plugin allow-version ... --accept-risk` 后重试安装。
   - profile 信息区可查看并撤销已有精确版本豁免。

6. **实例配置迁移**
   - 旧 `isolated_versions` 自动迁移到 `instances` + `homes/iN`。
   - 重复启动幂等；`state=deleting` 的实例删除会在下次启动续完。
   - 保留 `isolated_versions` 兼容镜像，旧命令行列表仍可读。

## 二、验收前置

- 建议在测试根 `E:\.LLM-AGENTS\deepseek-harness` 验收，不要直接用生产数据。
- 运行前备份 `config.json` 与 `versions/*/home`（如果测试根里有重要隔离数据）。
- 关闭已有的 `dsh-multiver.exe` 进程。

## 三、验收步骤

### A. 启动与迁移

1. 运行 `dsh-multiver.exe`。
2. 检查主界面版本显示 `v0.4.0-alpha.1`。
3. 检查 `config.json` 出现 `schema_version: 2`、`instances`、`homes/iN`。
4. 打开已安装版本列表，确认原有版本仍在。

### B. 插件批量更新

1. 点某个已安装版本的「插件」。
2. 选择「已安装」标签页，点「检查更新」。
3. 若有多个可更新项，确认出现「全部更新 (N)」。
4. 点「全部更新」→ 确认。
5. 观察进度与日志；结束后确认：
   - 成功项版本已变；
   - 失败项仍可加载（已回滚）；
   - 汇总数量正确。

### C. 单插件更新

1. 任意可更新插件点「更新」。
2. 确认成功提示与版本变化。
3. 失败时应看到日志错误，插件不应停留在已卸载状态。

### D. 精确版本豁免

1. 安装一个与当前 DSH 版本不兼容的插件（或使用验收包外的手工构造错误）。
2. 失败弹窗应出现「发现 N 个需要精确版本豁免的插件」和「允许全部 N 个并重试」。
3. 点击后应成功写入豁免并自动重试安装。
4. 打开 profile 信息区，确认可看到该豁免并撤销。

### E. 官方 bundle

1. 确认官方随附 bundle（如 `@deepseek-ai/dsh-base`）不出现「更新」按钮。
2. 确认批量更新不会包含官方 bundle。

### F. 回归

- 启动一个共享版本。
- 启动一个隔离版本。
- 两窗口并行，关闭 A 不影响 B。
- 关窗后子进程清理。
- 切换深/浅色，标题栏跟随。
