#### D15 处理说明（2026-10-21）

**结论：文件不拆，但内部重复已消除。**

**为什么不拆文件**
- 516 行由 **9 个完全独立的 CLI 命令**构成（`cmd_export` / `cmd_shortcut` / `cmd_copy_shared` /
  `cmd_clear_isolated` / `cmd_isolate` / `cmd_import` / `cmd_run` / `cmd_setup_runtime` / `cmd_update`），
  每个 50~70 行，彼此不共享状态、不互相调用。
- 这与 `commands.rs`（1687 行：命令 + 状态 + 辅助函数混杂）性质不同，**没有拆分的必要性**。
- 拆成 9 个文件（各 ~50 行）需增加 9 个文件头 + 9 处 `mod` 声明 + 9 处重导出，
  收益远小于成本，违反 Simplicity First。**判定为「观察」，不再动**。

**已修的部分：重复的进度回调**

`cmd_setup_runtime` 里 Node 与 pnpm 两段下载各写了一遍**完全相同**的进度闭包（17 行 × 2）。
已抽出 `misc.rs` 内的私有函数 `runtime_progress_cb(json)`，两处改为一行调用。净减 5 行，零行为变化。

**重复的成因（记录以防再犯）**——v0.2.9 期间分三步形成：

| 提交 | 日期 | 内容 |
| :--- | :--- | :--- |
| `192d993` | 2026-10-13 17:17 | 做便携 Node（94 行），pnpm 仅占位 |
| `7637458` | 2026-10-13 17:17 | 补便携 pnpm（29 行），**照抄 Node 的结构** |
| `9e17451` | 2026-10-14 02:45 | 加下载进度条，**给两段各写一遍相同闭包** ← 重复在此产生 |

当时未抽象不算错（第一批只有 Node，提前抽象是过度设计）；但**第三次出现同类模式时该抽象而没抽**。
教训：同一段逻辑出现第二次、且明确还会出现第三次时，就该抽。

**验证**：Windows 与 WSL 两平台 clippy 均干净、单测 104 通过、E2E 15 通过、CI `953eb8c` success。

#### D12 处理说明（2026-10-21）

**结论：应该拆，已拆。**（与 D15 的结论相反，理由见对比）

**判定依据（实测）**

| 区段 | 行数 | 内容 | 函数/结构数 |
| :--- | :--- | :--- | :--- |
| 22-338 | ~317 | 便携运行时（Node/pnpm 检测、下载、解压、PATH 计算） | **20** |
| 340-485 | ~146 | WebView2（注册表检测、原生框引导、Bootstrapper 下载） | **6** |
| 486-533 | ~48 | 测试（只测前半） | — |

**交叉引用为 0**：前半段引用 `webview2` 0 次，后半段引用 `node_`/`pnpm_`/`path_env` 0 次。

**与 D15 的关键区别**

| 维度 | D15（misc.rs 516 行） | D12（runtime.rs 533 行） |
| :--- | :--- | :--- |
| 内容性质 | 9 个**同质**命令 | **两个不相干领域** |
| 拆分后大小 | 各 ~50 行（太碎） | 各 321 / 147 行（合理） |
| 结论 | **不拆** | **拆** |

判据：**行数不是标准，"内容是否同质"才是**。同质命令再多也不该拆碎；异质领域哪怕只有 500 行也该分开。

**拆分结果**

- `mod.rs`（82 行）：模块声明 + 重导出 + 两者共用的 `RuntimeProgress` 与 `download_to`
- `bundled.rs`（321 行）：便携 Node / pnpm 的检测、下载、解压 + 测试
- `webview2.rs`（147 行）：WebView2 检测与安装引导

**踩坑（与 D14 同类）**：`download_to` 只被 `#[cfg(windows)]` 的 `install_webview2_bootstrapper` 使用，非 Windows 平台上成为 unused import，Linux clippy 报错。加 `#[cfg(windows)]` 门控解决，**WSL 复现并验证**。

**验证**：Windows 与 WSL 两平台 clippy 均干净、106 单测通过、命令契约一致（42/39）、E2E 15 通过。

## 五、维护约定

### 5.1 条目增删

- 发现新债 → 追加 D 条目（编号递增，**不回收已用编号**）
- 修复后 → 状态改 `✅ 已修（版本）`，债名用 `~~删除线~~` 标注
- 决定不做 → 移入"未做的修复"表，**同时**保留原 D 编号（避免链接失效）
- 条目**不删除**：无论已修、放弃还是证伪，都留在表里，保留完整决策链

### 5.2 记录深度：状态列不够，必须写"为什么"

**状态列只够写"做了什么"，写不了"为什么"**。以下情况必须在表格下方补 `#### D<编号> 处理说明`：

| 情况 | 必须记录的内容 |
| :--- | :--- |
| **判定"不修 / 观察"** | **为什么不修**（拆了收益小于成本的量化理由）、将来什么条件下重新考虑 |
| **做了但效果不符预期** | 实测数据 vs 预期数据、为何失败（如 P7-G：39.13s vs 38.16s） |
| **有争议的取舍** | 备选方案 + 选择理由（如 D13 为什么用 prune 而非 TTL） |
| **问题成因复杂** | 用 git 历史定位"哪次提交引入的"，列表记录，防再犯 |
| **修复影响面大** | 验证覆盖了哪些路径（单测 / E2E / 两平台 clippy / 实机） |

> **反例（今天修正过的 D15）**：原先只写「观察（重复已消除）」，后来者看不出：
> ① 为什么 516 行不拆？② 重复是怎么产生的？③ 抽出的函数叫什么？
> 补充后信息量与 D5/D6/D14 对齐。

**判断标准**：假如此条被另一个人（或半年后的自己）接手，他能否**不做重复调研**就做出同样决策？不能 → 记录不够。

### 5.3 证据必须实测，禁止凭记忆填

- 行数、单测数、耗时、文件大小等**一律现测**，不引用历史印象
- PowerShell 读文件务必加 `-Encoding UTF8`（**今天踩过**：漏了它导致 `misc.rs` 统计出 501 行，实际 47 行）
- 测量命令写在说明里，便于复核（如 `Get-ChildItem ... | ForEach { (Get-Content $_ -Encoding UTF8).Count }`）
- **数字前后矛盾时，以复测为准**，并记录发现过程

### 5.4 定期复检

- **每版发布后**：行数 / 单测数 / 文件清单等实测证据会随开发变化，需重新测量并更新
- **每次拆分或重构后**：核对受影响的条目（如 D5 拆分后 `mod.rs` 行数从 147 变 149）
- **发现文档与代码不符时**：立即修正并记录"何时发现的"，不要等下次

### 5.5 状态术语（固定用词）

| 状态 | 含义 |
| :--- | :--- |
| `✅ 已修（版本）` | 已完成，注明版本号 |
| `❌ 已实施但证伪` | 做了但验证无效，代码已回退（记录实测数据） |
| `观察` | 目前不是问题，但值得留意（必须写观察理由与触发条件） |
| `不修（原因）` | 评估后主动放弃（必须写原因与重新考虑条件） |
| `可接受` | 已知的轻微不足，不值得投入 |
