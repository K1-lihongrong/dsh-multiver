# 开发路线图（长期主义）

> 基线版本：v0.1.8 · 编写日期：2026-10-02
> 核心原则：**每一步的产出都应降低下一步的难度，而不是累积债务。**
> 排序：**1 → 2 → 4 → 3**（先铺基础设施，再理结构，最后跨平台）

---

## 〇、排序理由（为什么是 1-2-4-3）

| 步骤 | 产出 | 为下一步降低了什么难度 |
| :--- | :--- | :--- |
| **1 可观测性** | 完整、带时间戳、可回溯的日志 | 排查任何问题的成本 ↓ |
| **2 可验证性** | 关键路径自动化测试 + CI | 改代码的心智负担 ↓ |
| **3' 平台抽象** | Windows 专有逻辑收进可替换接口 | 跨平台适配难度 ↓ |
| **3 跨平台** | Linux 原生运行 | 未来维护面 ↓ |

链式逻辑：**观测**让问题可见 → **测试**让改动安全 → **抽象**让地基干净 → **跨平台**在干净地基上接入。
若先跨平台后抽象，等于"在乱结构上适配 Linux，再重构一次"，跨平台部分要重复验证。

---

# 阶段一：可观测性

## 目标
任何一次运行都有**完整、带时间戳、可回溯**的记录；偶发问题下次能自动现形。

## 现状盘点
| 数据流 | 现状 | 问题 |
| :--- | :--- | :--- |
| dsh 子进程 **stderr** | 落盘 `<home>/logs/dsh-stderr.log` | ✅ 已有 |
| dsh 子进程 **stdout** | 读线程读到 EOF **丢弃**（`launcher.rs:64-82`） | ❌ 最大盲区 |
| 主进程 Rust 错误 | 只经 `Err(String)` 弹 toast | ❌ 不落盘 |
| 启动失败分支 | 超时/提前退出/解析失败（`launcher.rs:110-126`） | ❌ 错误文本不落盘 |
| 前端 JS 错误 | 无任何捕获 | ❌ WebView 白屏无痕 |
| 安装进度 | 仅 `--debug-progress` 时落盘 | ⚠️ 默认不写 |

## 行动项

### 1.1 接入 `tauri-plugin-log`（主进程日志统一）
- `Cargo.toml` 加 `tauri-plugin-log = "2"`
- `lib.rs` 注册插件，配置 targets：
  - `Folder`：自定义到 `<manager_dir>/logs/`（保持便携自包含）
  - `Stdout`：开发期终端可见
  - `Webview`：转发到前端控制台（可选）
- 配置轮转（rotation）：单文件上限 + 保留份数，防膨胀
- 配置级别策略：默认 `Info`，`--debug` 参数时 `Debug`
- `capabilities/default.json` 加 `log:default` 权限

### 1.2 子进程输出完整落盘 + 会话日志
- **stdout 落盘**（改 `launcher.rs` 读线程）：拿到 URL 后不再丢弃，改为 append 到日志
- **会话日志**：每次启动生成带时间戳文件
  `<home>/logs/session-<yyyyMMdd-HHmmss>-<version>.log`
  内容：启动命令、环境变量、PID、stdout/stderr 实时追加
- **退出码记录**：在"提前退出"分支（`launcher.rs:116-118`）记录 status
  （说明：完整会话与退出码追踪需与 Job/kill 逻辑协调，若耦合风险高则降级为
  带时间戳的 stdout/stderr 分文件，不做 `child.wait()` 监控）

### 1.3 前端全局错误捕获
- `App.vue` `onMounted` 里加：
  `window.addEventListener("error", ...)`、
  `window.addEventListener("unhandledrejection", ...)`
- 新增 Tauri 命令 `log_frontend(msg)` → 写入 `app.log`

### 1.4 主进程错误统一落盘
- 新增 helper `log_error(mdir, ctx, msg)`（带时间戳，失败静默）
- 在各 `#[tauri::command]` 的 `Err` 分支、`launch_window`/`restart_version` 等
  错误返回点顺手调用

## 明确不做
- 不引入除 `tauri-plugin-log` 外的重型可观测性框架（Sentry/OTel 等留待未来）
- 不改变任何业务分支行为（纯旁路记录）

## 验收标准
- [ ] 一次"运行版本"后，`logs/` 下有该次会话的完整 stdout+stderr
- [ ] 一次失败的启动（如超时）在日志中可查到错误文本与时间
- [ ] 前端 JS 抛错后 `app.log` 有记录
- [ ] 日志文件有轮转，长期运行不无限增长

# 阶段二：可验证性

## 目标
关键路径有自动化测试兜底；改动不再"蒙眼"。

## 行动项

### 2.1 Rust 单元/集成测试
优先覆盖**纯逻辑、无副作用**的部分：
- `config.rs`：`Config` 读写、`resolve_root`、隔离版本判断
- `actions.rs`：`build_forward_script` 生成内容（脚本文本断言）
- `versions.rs`：`parse_url` / 版本列表解析 / `classify_error` 分类
- `launcher.rs`：`parse_url`（URL 解析是易错点，多给样例）

### 2.2 冒烟测试脚本
- 启动 → 解析 URL → 关闭 的端到端脚本（可复用 CLI 模式）
- 覆盖：`--list`、`--install`（可用 mock/npm 缓存）、`--maintenance`

### 2.3 扩展 CI
- `.github/workflows/release.yml` 已存在，新增 test job：
  `cargo test`、前端 `build`、冒烟脚本

## 明确不做
- 不追求高覆盖率（目标：关键路径有网即可）
- 不引入重量级 E2E 框架（Playwright 等）——Tauri 应用 E2E 成本高，性价比低

## 验收标准
- [ ] `cargo test` 全绿，覆盖上述模块
- [ ] CI 在 PR/push 时自动跑测试
- [ ] 一次"故意改坏"能被子测试捕获

# 阶段四：平台抽象层

> **范围严格限定为「隔离 Windows 专有逻辑」，不做任何投机性泛化。**
> 依据：`docs/Linux适配开发计划.md` 的「Windows 专有代码全清单」（27 项）

## 目标
把平台相关代码收进清晰、可替换的接口，为 Linux 铺好干净地基。

## 行动项

### 4.1 进程管理抽象（最高优先，🔴）
- `jobobj.rs` 是唯一 🔴 级项：Job Object `KILL_ON_JOB_CLOSE`（管理器退出即杀光子进程）
- 定义 `ProcessGroup` 抽象：`assign(child)` / `kill_tree(child)`
  - Windows 实现：现有 Job Object + `taskkill`
  - Linux 实现（占位）：进程组 / `prctl(PDEATHSIG)`
- `launcher.rs` 的 `kill_tree` 归入此抽象

### 4.2 启动与执行抽象
- dsh 入口路径：`.bin/dsh.cmd`（Win）↔ `.bin/dsh`（POSIX）
- 执行方式：`cmd /C`（Win）↔ 直接执行（POSIX）
- 隐藏/新控制台：`CREATE_NO_WINDOW` / `CREATE_NEW_CONSOLE`（Win）↔ 对应 POSIX 策略
- 归入 `launcher` 的 cfg 分支，确保每个专有 API 都在 `cfg(windows)` 内且有对应占位

### 4.3 桌面集成抽象
- 快捷方式：PowerShell COM `.lnk`（Win）↔ `.desktop`（POSIX）
- 桌面路径：注册表 `reg query`（Win）↔ XDG `user-dirs.dirs`（POSIX）
- 统一为 `DesktopIntegration` 接口

### 4.4 转发脚本抽象（补齐缺失的 cfg）
- ⚠️ `actions.rs` 的 `build_forward_script` **完全没有 cfg 分支**，Linux 会生成无用的 .cmd
- 抽为接口：Windows 生成 `dsh.cmd`，POSIX 生成 `dsh`（shell 脚本）
- 转发脚本目录：`%APPDATA%\npm`（Win）↔ PATH 内某处（POSIX）

### 4.5 机会主义项（不占独立阶段，改到时顺手做）
- **注入脚本外置**：`lib.rs` 的 `build_topbar_script`（手工拼接 100+ 行 JS）
  → 移到独立 `.js` 文件，用 `include_str!` 引入
  - 理由：它是"独立、前端、会被反复修改"的资产，冻在 Rust 字符串里持续收维护税
  - 时机：阶段一注入日志/错误捕获时会改到它，一并搬家
- `lib.rs` 按职责拆分（命令层/窗口层/脚本），**不占阶段**，测试就绪后机会主义推进

## 明确不做
- 不设计"通用跨平台框架"，只做"Windows 逻辑隔离 + POSIX 占位"
- 不新增 Windows 用不到的概念（等真正做 Linux 再按需扩展）

## 验收标准
- [ ] 每个 Windows 专有 API 都在 `cfg(windows)` 内，有对应 `cfg(not(windows))` 占位
- [ ] `launcher`/`actions`/`versions` 中平台差异集中在少量接口点
- [ ] 编译期：Linux 目标可 `cargo check` 通过（占位可运行）
- [ ] 注入脚本已外置为 `.js`（若做）

# 阶段三：跨平台（Linux）

> 在阶段四的干净地基上接入，是"填空"而非"重写"。

## 目标
dsh-multiver 在 Linux 原生运行（不依赖 Wine / 不做远程）。

## 行动项

### 3.1 落实清单中的 🟢 简单项
- dsh 入口 `.bin/dsh`、直接执行、转发脚本目录、硬编码 `dsh.cmd` 删除点等

### 3.2 落实 🟡 中等项
- `taskkill` → POSIX 信号杀进程树（阶段四抽象后的 Linux 实现）
- `.lnk` → `.desktop`、`reg query` → XDG
- `CREATE_NEW_CONSOLE` → 终端模拟策略
- `IDLE_PRIORITY_CLASS`（maintenance）→ `nice`
- `GetConsoleMode`（cli TTY 判断）→ `isatty`

### 3.3 落实 🔴 重设计项
- `jobobj.rs` 的 Linux 进程组实现（阶段四已留接口）

### 3.4 WebView 差异
- WebView2 数据目录（每版本独立）→ Linux WebKit 的 data dir
- UA、缓存策略的对应

### 3.5 构建与发布
- `Cargo.toml` 的 `windows-sys` 已在 `[target.'cfg(windows)']`（✅ 无需改）
- `.github/workflows/release.yml`：加 `ubuntu-latest`，形成构建矩阵
- 图标、bundle target 适配

### 3.6 验证
- 在真 Linux 上验证所有 `cfg(not(windows))` 分支
  （注意：现有这些分支**大多是照抄的 fallback，从未在真 Linux 验证**）

## 明确不做
- 不做 macOS（除非有明确需求，架构上不排斥但不在本期）
- 不引入 Wine / 远程方案（目标就是原生）

## 验收标准
- [ ] Linux 上可安装/卸载/运行版本，内嵌窗口正常
- [ ] 进程无孤儿残留（等价于 Windows 的 Job Object 保障）
- [ ] CLI 模式在 Linux 正常
- [ ] CI 产出 Linux 安装包

---

## 附：阶段依赖与风险

| 阶段 | 依赖 | 主要风险 | 缓解 |
| :--- | :--- | :--- | :--- |
| 1 可观测性 | 无 | 日志膨胀、与子进程读线程耦合 | 轮转 + 降级方案 |
| 2 可验证性 | 1（失败可诊断） | 测试维护成本 | 只覆盖关键路径 |
| 4 平台抽象 | 2（安全网） | 过度抽象、猜错边界 | 严格限定"隔离 Win 逻辑" |
| 3 跨平台 | 4（干净地基） | cfg 分支从未真机验证 | 真 Linux 上逐项验证 |

## 附：非阶段的机会主义项
- 注入脚本外置（见 4.5）
- `lib.rs` 通用拆分（与跨平台正交，测试就绪后推进）
