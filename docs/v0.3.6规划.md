## 一、要解决的问题

`docs/插件兼容矩阵.md` 当前结论是「最低已验证版本 `0.1.5-rc.3`」，但这句**只说明 rc.3 能用**，不能说明 rc.3 以下都不能用。同时，当前 `verifiedDshVersions` 最后登记的是 `0.2.1-rc.3`，之后发布的版本一个都没验证过。

后果：用户在未验证版本上遇到问题时，**无法判断是插件 bug 还是 dsh 版本差异**。插件页面会显示「未验证版本」黄条，但用户拿不到「到底支不支持」的答案。

## 三、判定口径（必须先定，否则结论无法比较）

每个版本按矩阵现有 5 列判定：装插件 / 启动 / `state` / 401 鉴权 / 405 方法。

**「支持」** = 5 列全 ✅。
**「不支持」** = 插件装上但某项端点行为不符合预期（这是插件要修的问题）。
**「无法判定」** = dsh 自身装不上或起不来，与插件无关。**必须写明具体错误**，不能笼统写「失败」。

> 关键区分：`fs-ext` 编译失败、Cordis HMR 报错属于 dsh 自身问题 → 「无法判定」而非「不支持」。这个口径写进文档，避免后人误读为插件不兼容。

## 四、执行方法

沿用 `docs/插件兼容矩阵.md` 第 57 行的复现方法，不另造流程：

1. 用 multiver 在测试根 `E:\.LLM-AGENTS\deepseek-harness\` 装目标版本
2. 为该版本准备独立 `DSH_HOME`（`%TEMP%\compat-<版本>`）
3. `dsh plugin --profile web add <插件 tgz>`
4. `dsh web --port <独立端口> --no-open` 启动
5. 验 `state`（带 token）/ 401（不带 token）/ 405（GET）
6. 记录结果，清理临时版本与 home

**测试纪律**（沿用现有约定）：测前快照真实 `config.json` 的 SHA256，测后核对未变；临时 `DSH_HOME` 全部放 `%TEMP%`，测完移入回收站；临时版本用 `uninstall` 清理，不留 `broken_versions` 标记。

## 六、风险与边界

| 风险 | 应对 |
| :--- | :--- |
| 旧版本 `fs-ext` 编译失败，无法验证 | 标记「无法判定」，记录错误原文，不强行绕过 |
| 早期版本依赖已下架私有包 | 安装失败即记「无法判定」，不重试换源 |
| 测试版本多，磁盘占用 | 每测完一个立即 `uninstall`，不留存量 |
| 误动真实数据根 | 全程用独立 `DSH_HOME`，测前快照 `config.json` |

**不在本轮范围**：改插件兼容性代码、放宽安装层约束（当前已是零约束）、补 macOS 验证。
