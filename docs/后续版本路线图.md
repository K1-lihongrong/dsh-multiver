## 一、版本序列总览

```
v0.3.6 ──▶ v0.3.7 ──▶ 0.4.0-alpha.1 ──▶ 0.4.0-alpha.2 ──▶ 0.4.0-alpha.3 ──▶ v0.4.0 ──▶ v0.4.1
  (现状)   安全与契约加固        类型与状态收口      适配层与任务收敛    暴露实例模型      位置防呆 + 安全模式 + 标题栏修复
           1–1.5 周             2–2.5 周            2.5–3 周            2.5–3 周          补丁 + 救援
           5–7 人日             12–16 人日          22.5–30 人日        9.5–11 人日        4.1–6.0 人日
           ✅ 发 Release        ❌ 不发 Release      ❌ 不发 Release      ✅ 发 Release      ✅ 发 Release
```

**合计 49–64 人日（中位 ≈ 56.5），约 10–13 周；v0.4.1 另计 4.1–6.0 人日（含 2026-11-20 追加的安全模式）。** 人日口径：1 人日 = 1 个完整工作日（约 8 小时，含调试），按「熟悉该栈的 1 人 + AI 辅助」估算。

### 版本号语义

- **v0.3.7** 是 patch 号，因为全部是 bugfix + 补验证 + 减代码，不产生破坏性接口。
- **0.4.0-alpha.N** 明确表示「v0.4.0 的开发过程」，不是稳定版；装的是破坏性结构改造（`ProcMap` key 类型、`config.json` 结构、插件域拆分）。用 `0.3.8 / 0.3.9` 会误读为 patch 级修复。
- **alpha 周期内仍打轻量 tag**（`git tag 0.4.0-alpha.1`，不推 Release）。用途：回滚锚点、CHANGELOG 追溯、bug 复现。成本一条命令。
- **v0.4.1** 仍是 patch 号（v0.4.0 之后的补丁），但含安全模式这一救援能力；不产生破坏性接口，配置结构与命令契约不变。

### 「不发 Release」的准确含义

| 事项 | alpha 周期内 |
| :--- | :---: |
| 打轻量 tag（`0.4.0-alpha.N`） | ✅ 做 |
| 推 GitHub Release / 写 RELEASE_NOTES | ❌ 不做 |
| 改 README 的下载链接 | ❌ 不做 |
| main 分支可编译、可运行、测试全绿 | ✅ **必须** |
| 每个 PR 独立可回滚 | ✅ **必须** |

### 4.3 顺序

**M1 必须最先**，不是因为逻辑上先，是因为编译器的顺序：newtype 一旦引入，所有用到的地方都会编译报错——这是免费的全量扫描。若先做 M2，会遇到「迁移函数要返回什么类型」而这时 `InstanceId` 还不存在，只能先用 `String`，做完 M1 再回来改，典型的改两遍。

**插件批量更新/回滚放在 M3 之后、W4 之前**：它依赖 M3 的 `AppCtx` 命令签名，避免同一批插件命令改两遍；同时先于端口抽象落地，W4 可复用其 runner 接口。

## 七、工程守则（全周期适用）

### 7.1 CI 门禁（每个 PR 合并前）

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
pnpm build
```

alpha 周期内不额外增加 CI 步骤，沿用现有 `ci.yml`。

### 7.2 每个周期结束的额外验证

| 周期 | 额外验证 |
| :--- | :--- |
| v0.3.7 | `cargo test -- --ignored`（新增契约测试） |
| alpha.1 | 旧 `config.json` 样本迁移等价性 |
| alpha.2 | 兼容矩阵 × 插件操作 |
| v0.4.0 | 兼容矩阵 × 实例维度 + 回归清单全跑 |

### 7.3 PR 拆分原则

1. **纯新增与改逻辑分开**：新增测试、新增脚本单独 PR，回滚成本为零
2. **同一批文件的改动可按回滚粒度拆**：如 A1 与 A2 虽同批文件，但 A2 可能触发隐藏依赖，单独拆
3. **格式化与批量改名单独立项**（沿用 D2 纪律）

### 7.4 什么时候可以偏离守则

**只有一种情况**：某个 PR 需要先破坏 main 才能验证（例如 M1 newtype 化必须一次改完 12 个调用点，不能分批）。处理方式：

- 在分支上完成后，一次合并
- 合并前必须 `cargo check` + `cargo test --lib` 全绿
- 合并后立刻验证 main 可运行

**不能接受的是**：为了「看起来进度快」，把 main 保持在不可编译状态超过一天。

> **触发 1（2026-11-12）**：便携版放在 DSH workspace（带 `Everyone` 的 `DeleteSubdirectoriesAndFiles` deny）时，WebView2 初始化失败，用户看不到可理解的错误，只看到窗口不出现或 `0x800700AA` / `0x8000FFFF`。v0.4.0 不阻塞；排入 v0.4.1。

### 10.6 安全模式（GAP-024，2026-11-20 追加）

> **定位**：主界面起不来时的最后入口，不是日常错误提示，也不替代 §2.6 的数据根横幅。
> **原则**：能诊断、能备份、能重置、能告诉用户最后怎么重装；不静默删数据、不自动修 ACL、不自动搬 exe。

#### 10.6.1 三层兜底

| 层 | 触发 | 载体 | 能做什么 |
| :--- | :--- | :--- | :--- |
| 1 | Tauri / WebView2 初始化之前就失败（exe 目录不可写、WebView2 缺失） | Win32 `MessageBoxW`（F-1 / 现有 WebView2 提示） | 说明路径、原因、正确放置位置、日志位置；WebView2 缺失给安装指引 |
| 2 | Tauri 能起，但主界面白屏/JS 崩溃/连续启动失败/配置损坏 | 独立安全模式窗口（静态页 + 独立 WebView2 数据目录） | 诊断、导出、重置配置/缓存、初始化工作环境、卸载重装指引 |
| 3 | 安全模式窗口也起不来（WebView2 损坏） | 原生 `MessageBoxW` + 外部步骤 | 日志/数据目录路径、修 WebView2、重新下载 exe 的步骤 |

**边界**：安全模式不追求「连 WebView2 都坏了还能现场修」——那一层只能靠修 WebView2 或重装。能保证的是：**Tauri 能起时，主界面坏了仍有一个可操作的界面**；Tauri 起不来时，仍有原生提示。

#### 10.6.2 范围

| 项 | 内容 | 人日 |
| :--- | :--- | ---: |
| S-1 | **启动守卫与进入路径**：`--safe-mode`；连续 3 次非正常退出后自动进入；前端 `app_ready` 30 秒未握手时打开安全模式窗口（不杀主窗口）；`Config::load_checked` 暴露「本次是否发生损坏回退」标志，安全模式据此进入提示；单实例转发 `--safe-mode`；安全模式期间跳过自动维护/更新检查/自动启动 DSH | 0.5–0.7 |
| S-2 | **安全模式窗口与界面**：独立 `safe-mode` 窗口（原生标题栏、760×620、可缩放），Vite 第二入口的静态 HTML/JS（不加载 Vue、不启动 DSH、不访问网络），独立 WebView2 数据目录（失败退回 `%TEMP%`），5 语静态文案；只保留「发生了什么 / 环境信息 / 最近错误 / 修复动作 / 重装指引」 | 0.9–1.2 |

**S 小计 3.5–4.8 人日；F-1..F-4 小计 0.6–1.2；v0.4.1 合计 4.1–6.0 人日。** 若排期必须压缩，先减 S-3 与 S-5 的文档深度，**不得减 S-1/S-2**（没有入口和兜底窗口，安全模式不成立）；「初始化工作环境」也不能省，它是用户说的最后一步。

#### 10.6.3 进入与退出

1. **手动**：`dsh-multiver.exe --safe-mode`。必须在 CLI 分流之前识别；已有实例收到时由单实例回调打开安全模式，不转发成普通启动。
2. **连续失败**：启动前在 `<root>/state/startup.json` 记 `attempts` / `clean_exit`；正常退出或前端 `app_ready` 后清零。上次 `clean_exit=false` 时累加，达到 3 次自动进入安全模式。被任务管理器强杀也算一次——这是有意的：连续三次非正常退出，用户需要的是修复入口，不是第四次黑屏。
3. **白屏看门狗**：前端首屏完成后调用 `app_ready`；30 秒未收到时打开安全模式窗口，**不关闭主窗口**。主窗口随后恢复时，安全模式显示「主界面已恢复，可关闭本窗口」。
4. **配置损坏**：`Config::load_checked` 已把原文件改名并回退默认；需要额外暴露「本次发生了损坏回退」标志，安全模式据此进入并说明「已备份/已回退」，用户可一键继续正常启动。
5. **普通运行错误不进入**：dsh 启动失败、网络失败、插件安装失败仍走现有错误提示；安全模式只在「管理器自身/主界面」故障时出现，避免告警疲劳。

**退出**：点「继续正常启动」清空计数并重开主窗口；关闭安全模式且没有主窗口时，进程干净退出，不留子进程。

#### 10.6.4 修复动作（从轻到重）

| 动作 | 做什么 | 保留什么 | 风险/提示 |
| :--- | :--- | :--- | :--- |
| 导出诊断 | 日志尾部（≤2 MB）、脱敏 `config.json`、`startup.json`、环境 JSON、版本/实例清单打包 | 不改任何数据 | 日志中的 `token=`、`sk-` 等必须脱敏；不导出完整会话内容 |
| 重置配置 | 备份 `config.json`（含 `.broken-*`）到 `backup/`，写回默认配置 | 已安装版本与 `homes/` 原地保留 | 数据根回到 exe 所在目录；已安装版本不会消失，但列表要重新指定原数据根才能看到 |
| 重置 WebView2 数据 | 主窗口 WebView2 数据目录 + `<root>/webview/` 移入 `trash/safe-reset-<ts>/` | 版本、实例 home、配置不变 | 会重置主题/语言/安装源等界面偏好；不碰 DSH 会话 |
| 初始化工作环境 | 把 `versions/`、`home/`、`homes/`、`store/`、`cache/`、`state/`、`webview/`、`logs/`、`config.json` 移入 `<root>/trash/safe-reset-<ts>/`，重建默认目录 | 未知文件、`assets/`、`trash/` 本身保留 | 已安装版本需重装；实例/共享 home 中的会话与凭据也在 trash 中，可手工找回；必须二次确认 |
| 卸载重装指引 | 打开数据目录/日志/下载页，复制路径；说明「退出后替换 exe / 删除数据目录 / 重装 WebView2」的步骤 | 不自动删 exe、不自动下载 | 便携版没有安装器；exe 不能自己删自己 |

**执行方式（重要）**：除导出诊断外，涉及移动/删除的动作都不当场执行，而是写 `<root>/state/safe-repair.json`（动作 + 时间 + 目标根），提示「重启后生效」，然后退出。下次启动在 `run()` 最前面（`Config::load_checked` 与 staged 更新之前）读取并执行；执行前先把意图读入内存，执行后删除意图文件。理由：Windows 上主窗口的 WebView2 数据、日志、`config.json` 可能仍被当前进程占用，当场删必然失败；延后到下一次启动前，锁已释放，行为可复现。

**安全约束**：
- 只处理 `<root>` 下的**已知目录名**与 `config.json`；移动前逐个规范化绝对路径，拒绝 `..`、拒绝根本身、拒绝数据根之外的路径。
- 不删除：一律 rename 到 `trash/safe-reset-<ts>/`；失败时保留原目录并报告，不继续「部分初始化」。
- 不碰官方 `~/.dsh`、不碰 `assets/`、不碰未知文件、不碰 exe。
- 诊断包脱敏；不收集遥测、不上传。

#### 10.6.5 技术约束

- 安全模式窗口用独立 `data_directory`，不复用主窗口的 WebView2 缓存；否则主缓存损坏时兜底窗口一起失效。
- 静态页作为 Vite 第二入口构建，**不 import Vue、不启动 DSH、不发网络请求**；独立 capability（`safe-mode.json`），只放窗口控制、opener 与安全模式自己的命令。
- 安全模式命令集中在 `commands/safe_mode.rs`；诊断/修复的纯逻辑放在 `safe_mode.rs`，可单测，不依赖 Tauri。
- 修复意图必须是幂等的：同一动作重复启动不会重复移动；目标不存在视为已完成；`trash` 名带时间戳，避免覆盖。
- 5 语静态文案；系统语言不在支持列表时回退中/英。i18n 不走 Vue 的运行时字典，避免主界面坏了文案也拿不到。
- 安全模式不启动自动维护、更新检查、插件扫描；不打开任何 dsh 窗口。
- 与 §2.5 的关系：保留「损坏自动备份 + 回退默认」的文件处理，只新增「本次启动进入安全模式说明」；不改变备份文件名和回退语义。

#### 10.6.6 验收

- [ ] `--safe-mode` 能打开静态安全模式窗口；主界面正常时行为不变。

- [ ] 初始化工作环境：已知目录与 `config.json` 全部在 `trash/safe-reset-<ts>/`；未知文件、`assets/`、`trash/` 保留；重启后自动重建默认目录；root == exe 目录时同样成功。

- [ ] 单实例：已运行时执行 `--safe-mode` 能在现有进程打开安全模式；不同副本仍按原逻辑拒绝。
- [ ] WebView2 不可用：仍走原生提示，不进入崩溃循环。
- [ ] 安全模式自身创建失败：原生提示一次并干净退出，不递归进入安全模式。

#### 10.6.7 顺序与依赖

## 十二、开始的第一步

**从 §3.2 的 A1 开始，不要从 alpha.1 开始。**

理由：

1. A1 只改 `launch_window` 一处 + 删 4 个 `listen_any`，**半天可完成**
2. 它是安全修复，不是债——拖到 v0.4.0 意味着风险窗口再开 9–12 周
3. 它是后续周期的探路石：如果 A1 改完发现内嵌窗口有意外依赖（例如某个 IPC 调用藏在 `topbar.js` 深处），可以在 v0.3.7 内消化，而不是在 alpha 周期的大改动中暴露

**A1 完成后的验收（最直接）**：

打开两个版本的窗口，在版本 A 的 dsh 页面控制台执行：

```js
emit('topbar-ctrl', {action:'close', version:'<版本B>'})
```

**版本 B 的窗口不应关闭。** 这是来源校验是否真正到位的最直接验证。
