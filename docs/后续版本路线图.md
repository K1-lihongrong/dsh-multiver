## 一、版本序列总览

```
v0.3.6 ──▶ v0.3.7 ──────────▶ 0.4.0-alpha.1 ──▶ 0.4.0-alpha.2 ──▶ v0.4.0
  (现状)   安全与契约加固        类型与状态收口      适配层与任务收敛    实例模型落地
           1–1.5 周             2–2.5 周            2.5–3 周            2–3 周
           5–7 人日             12–16 人日          22.5–30 人日        12–18 人日
           ✅ 发 Release        ❌ 不发 Release      ❌ 不发 Release      ✅ 发 Release
```

**合计 51.5–71 人日（中位 ≈ 61），约 10–14 周。** 人日口径：1 人日 = 1 个完整工作日（约 8 小时，含调试），按「熟悉该栈的 1 人 + AI 辅助」估算。

### 版本号语义

- **v0.3.7** 是 patch 号，因为全部是 bugfix + 补验证 + 减代码，不产生破坏性接口。
- **0.4.0-alpha.N** 明确表示「v0.4.0 的开发过程」，不是稳定版；装的是破坏性结构改造（`ProcMap` key 类型、`config.json` 结构、插件域拆分）。用 `0.3.8 / 0.3.9` 会误读为 patch 级修复。
- **alpha 周期内仍打轻量 tag**（`git tag 0.4.0-alpha.1`，不推 Release）。用途：回滚锚点、CHANGELOG 追溯、bug 复现。成本一条命令。

### 「不发 Release」的准确含义

| 事项 | alpha 周期内 |
| :--- | :---: |
| 打轻量 tag（`0.4.0-alpha.N`） | ✅ 做 |
| 推 GitHub Release / 写 RELEASE_NOTES | ❌ 不做 |
| 改 README 的下载链接 | ❌ 不做 |
| main 分支可编译、可运行、测试全绿 | ✅ **必须** |
| 每个 PR 独立可回滚 | ✅ **必须** |

### 4.3 顺序

**M1 必须最先**，不是因为逻辑上先，是因为编译器的顺序：newtype 一旦引入，所有用到的地方都会编译报错——这是免费的全量扫描。若先做 M2，会遇到「迁移函数要返回什么类型」而这时 `InstanceId` 还不存在，只能先用 `String`，做完 M1 再回来改，典型的改两遍。

**插件批量更新/回滚放在 M3 之后、W4 之前**：它依赖 M3 的 `AppCtx` 命令签名，避免同一批插件命令改两遍；同时先于端口抽象落地，W4 可复用其 runner 接口。

## 七、工程守则（全周期适用）

### 7.1 CI 门禁（每个 PR 合并前）

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
pnpm build
```

alpha 周期内不额外增加 CI 步骤，沿用现有 `ci.yml`。

### 7.2 每个周期结束的额外验证

| 周期 | 额外验证 |
| :--- | :--- |
| v0.3.7 | `cargo test -- --ignored`（新增契约测试） |
| alpha.1 | 旧 `config.json` 样本迁移等价性 |
| alpha.2 | 兼容矩阵 × 插件操作 |
| v0.4.0 | 兼容矩阵 × 实例维度 + 回归清单全跑 |

### 7.3 PR 拆分原则

1. **纯新增与改逻辑分开**：新增测试、新增脚本单独 PR，回滚成本为零
2. **同一批文件的改动可按回滚粒度拆**：如 A1 与 A2 虽同批文件，但 A2 可能触发隐藏依赖，单独拆
3. **格式化与批量改名单独立项**（沿用 D2 纪律）

### 7.4 什么时候可以偏离守则

**只有一种情况**：某个 PR 需要先破坏 main 才能验证（例如 M1 newtype 化必须一次改完 12 个调用点，不能分批）。处理方式：

- 在分支上完成后，一次合并
- 合并前必须 `cargo check` + `cargo test --lib` 全绿
- 合并后立刻验证 main 可运行

**不能接受的是**：为了「看起来进度快」，把 main 保持在不可编译状态超过一天。

| 诱惑 | 为什么不做 |

## 十一、开始的第一步

**从 §3.2 的 A1 开始，不要从 alpha.1 开始。**

理由：

1. A1 只改 `launch_window` 一处 + 删 4 个 `listen_any`，**半天可完成**
2. 它是安全修复，不是债——拖到 v0.4.0 意味着风险窗口再开 9–12 周
3. 它是后续周期的探路石：如果 A1 改完发现内嵌窗口有意外依赖（例如某个 IPC 调用藏在 `topbar.js` 深处），可以在 v0.3.7 内消化，而不是在 alpha 周期的大改动中暴露

**A1 完成后的验收（最直接）**：

打开两个版本的窗口，在版本 A 的 dsh 页面控制台执行：

```js
emit('topbar-ctrl', {action:'close', version:'<版本B>'})
```

**版本 B 的窗口不应关闭。** 这是来源校验是否真正到位的最直接验证。
