# 插件面板「取消 / 中止」设计（讨论稿）

> **状态：讨论稿 v3（取消挂起，等官方）。** 编写：2026-10-21 · 关联：[开发缺口 B1-04](开发缺口.md)、[双向桥交接文档](dsh双向桥-交接文档.md)
> v2：补充官方实现对照（§15）；v3（2026-10-21 决策）：**取消不实现、挂起等官方**；当前实现已与官方标签/诊断语义对齐，见 §16.6 / §16.7。

---

## 0. 一句话结论

「取消」不是一个按钮，而是**操作生命周期治理**：
把外部包管理器（pnpm / `dsh plugin`）带来的不可见、不可控、不可逆的副作用，变成**可见、可中断、可解释、可恢复**的终态。

---

## 1. 背景与现状

插件面板（B1）通过 `dsh plugin --profile <p> <pnpm 参数>` 管理某个 dsh 版本的插件。`pnpm add` 在慢网络下可能持续 1~2 分钟，`remove` 通常较快。

**当前实现（`src-tauri/src/dsplugins.rs` / `commands/plugins.rs`）**：

- `ds_plugin_action` 为 async + `spawn_blocking`，超时 300s；
- 执行中按行 emit `ds-plugin-progress`，前端有输出面板；
- 超时分支为 `child.kill()` + `child.wait()`；
- 前端只有 `busy` 状态，**没有取消入口**；
- spawn 时**未**接 `jobobj`（Windows Job Object / Unix 进程组）。

**已存在的缺陷（与是否加按钮无关）**：

> `child.kill()` 只杀直接子进程——Windows 上是 `cmd.exe`，Unix 上是 dsh 的 node 进程；**pnpm 及其子进程可能继续运行**。也就是说，当前“超时中止”名不副实，可能残留后台进程继续写盘。

---

## 2. 元目的：这个功能到底在解决什么

**表层需求**：装插件等太久，想中止。

**真实痛点**（拆开）：

1. **不可预期**：不知道要等多久、是否卡住；
2. **不可控**：没有脱身手段；
3. **不可信**：中止后不知道 profile 处于什么状态、下一步该做什么。

**系统视角**：这个面板本质是「给外部包管理器套一个 GUI 壳」。GUI 壳的第一职责不是功能齐全，而是把**不可见的后台副作用**变成**可见、可控、可恢复**。

因此本功能的元目的是：

> **操作生命周期治理**——任何一次插件操作，从开始到终态，都能被看见、被中断、被解释、被恢复。

**成功判据**不是“有取消按钮”，而是：**任何终态都可解释、系统无残留、用户知道下一步**。

---

## 3. 第一性事实（设计约束）

| # | 事实 | 推导 |
| :-- | :--- | :--- |
| A1 | pnpm 没有事务 / 回滚 | 中止必然可能留下“半装”状态，**不能承诺“取消即干净”** |
| A2 | 杀进程 ≠ 副作用停止 | 杀父不杀孙、pnpm worker、OS 缓存都会让“取消后”状态仍变化；必须管**进程树**并**确认**退出 |
| A3 | UI 状态必须由可观测证据推导 | 不能因为“发了 kill”就显示“已取消”；终态 = 进程树已退 + 输出 EOF + 退出码/原因 |
| A4 | dsh profile 是外部系统状态 | 我们只是调用方，无法保证其一致性，只能**观察 + 修复 + 诚实提示** |
| A5 | 等待的痛感来自不确定性，而非时长 | 进度/阶段/超时可见性本身就能缓解；取消是最后手段 |
| A6 | 信任来自失败可恢复，而非从不失败 | 恢复路径比“更少失败”更重要 |

---

## 4. 由事实导出的目标优先级

> **G1 终态可信 > G2 无残留 > G3 可恢复 > G4 可预期 > G5 UI 简洁**

反例说明顺序：若先做取消按钮、后做进程树治理，用户点「取消」→ UI 显示已取消 → pnpm 仍在后台写盘。
这**比没有按钮更糟**：它直接破坏 G1，而 G1 是信任的根。

---

## 5. 重新定义「取消」（语义契约）

**取消 ≠ 回滚。取消 = 中止 + 进入一个被明确标记的「可能不一致」状态 + 给出恢复路径。**

契约条款：

1. 不得出现“已取消 = 状态干净”的暗示；文案必须写明**可能未完成**。
2. 终态必须由可观测证据决定，不得由“kill 已发出”决定。
3. 无法确认终止时，必须允许 **Unknown（未知）** 这个终态，而不是假装成功。
4. 每个终态都必须附带**下一步动作**（重试 / 修复 / 刷新 / 查看输出）。
5. 修复动作不是“重试 add”（可能叠加错误），而是**收敛到声明状态**：`pnpm install`（按 lockfile 重建 node_modules），必要时建议重新初始化 profile。

---

## 6. 状态机（设计核心，不是 UI）

```
Idle ──启动──▶ Running ──┬─▶ Succeeded   (exit 0，进程树已退)
                          ├─▶ Failed      (exit ≠ 0)
                          ├─▶ TimedOut    (超时 → kill_tree → 确认退出)
                          ├─▶ Cancelled   (用户取消 → kill_tree → 确认退出)
                          └─▶ Unknown     (kill 后仍无法确认进程退出)
                Running ──取消──▶ Cancelling ──确认退出──▶ Cancelled / Unknown
```

关键点：

1. **Cancelling 是独立状态**：点击后 UI 立刻进入“正在取消…”，但终态要等**进程树确认退出**，不能等 `kill()` 返回；
2. **Unknown 必须存在**：强杀后若无法确认孙进程退出，如实提示“可能仍在运行”，并提供“重新检查 / 再取消”；
3. **每个终态都有**：i18n 文案、可执行的下一步、输出面板证据（A3）；
4. 所有终态都刷新 `ds_list_plugins`，以实际状态覆盖猜测。

## 7. 设计空间与方案对比

| 方案 | 内容 | 评价 |
| :--- | :--- | :--- |
| A. 只改预期 | 文案说明“可能较慢”，不做中止 | ❌ 不解决“不可控” |
| B. 只做超时杀树（P0） | `jobobj` + `kill_tree` + 终态确认 | ✅ **必做**，修当前“假中止”缺陷 |
| C. 协作式取消（P2） | `AtomicBool`/取消令牌 + `kill_tree` | ✅ 推荐，UI 可控 |
| D. 取消 + 回滚快照 | 备份 node_modules / lockfile，取消后还原 | ❌ pnpm 无事务、快照成本不可接受 |
| E. 任务化 | 操作脱离面板继续、完成通知、历史 | ⏸ P3 暂缓（当前场景收益低） |
| F. 优雅中断（Ctrl-C / SIGINT） | 共享控制台 + `GenerateConsoleCtrlEvent` | ❌ Windows 不可靠、可能波及宿主控制台 |

**推荐路径：B → 一致性契约（P1）→ C（P2）→ E（P3，可选）。**

---

## 8. 一致性契约与恢复路径（决定体验的部分）

终态后统一执行：

1. 刷新 `ds_list_plugins`（实际状态优先）；
2. 做一次“声明 vs 实际”检查：`dependencies` 有 / `node_modules` 缺，或反之 → 标黄提示“可能不完整”；
3. 提供「修复 profile」动作：`dsh plugin --profile <p> install`（转发 pnpm install，按 lockfile 收敛）；
4. **不做整体回滚**（pnpm 无快照）；
5. **不做持久化“损坏标记”**（避免改 config/profile 结构），用“本次会话终态 + 提示”表达。

## 9. 接口草案（待讨论，不是最终实现）

后端：

```text
命令：ds_cancel_action(version, profile) -> Result<(), String>
      仅置位取消令牌；真正终止由运行中的循环执行 kill_tree。

事件：ds-plugin-progress { version, profile, line }       // 已有
      ds-plugin-done    { version, profile, outcome, cancelled, output }  // 新增

运行注册表：PLUGIN_RUNS: Mutex<HashMap<String /*version::profile*/, Arc<AtomicBool>>>
            （仅内存，进程退出即失；无需持久化）
```

前端状态映射：

```text
busy=false                     → Idle
busy=true && !cancelling       → Running
cancelling=true                → Cancelling
收到 done(outcome)             → 对应终态 + 提示 + 刷新
```

## 10. 验收标准（可测）

1. **无残留**：假脚本再 spawn 孙进程 → 取消/超时后 5s 内孙进程必须不存在（Rust 测试可断言）；
2. **终态可信**：kill 后确认退出才进入 `Cancelled`；无法确认则显示 `Unknown`；
3. **响应性**：点击取消 1s 内 UI 进入 `Cancelling`（不等待后台完成）；
4. **可解释**：5 种终态各有文案 + 下一步动作；
5. **可恢复**：模拟半装状态，「修复」动作能跑通或给出明确指引；
6. **无回归**：现有单测 / E2E 全绿。

---

## 11. 明确不做（及理由）

- **取消即回滚**：pnpm 无事务，快照成本不可接受；
- **SIGINT 优雅中断**：Windows 需共享控制台，不可靠且可能波及宿主；
- **跨会话任务队列 / 历史**：当前是本地单机 GUI，收益低、状态复杂；
- **持久化“损坏”标记**：会引入新的 config/profile 结构，违背“不自造状态”的约定。

## 12. 开放问题（实现前需要讨论）

1. **取消入口范围**：只对 `add` 提供取消，还是 `add` / `remove` 都提供？
2. **修复动作呈现**：做成按钮（跑 `pnpm install`），还是仅文案引导用户手动处理？
3. **Unknown 判定阈值**：kill 后等待几秒仍无法确认就进入 Unknown（3s / 5s？）
4. **取消后是否自动重试**：不自动（推荐）？还是弹提示“重试 / 修复 / 关闭”？
5. **进度事件粒度**：逐行 emit，还是节流到 100~200ms 一批（避免事件风暴）？
6. **超时时长**：固定 300s，还是可配置（设置项）？
7. **是否推进 P3 任务化**：后台继续 + 完成通知，是否属于本阶段？
8. **取消后状态表达**：只在本次会话提示，还是允许写 profile 内标记文件（跨会话可见）？

## 15. 官方实现对照（2026-10-21 调研，结论修订）

> 调研对象：官方文档 [插件市场](https://deepseek-harness.github.io/deepseek-harness/guide/plugin-market) +
> 本机已安装的官方包 `@deepseek-ai/dsh-plugin-manager`、`@deepseek-ai/dsh-client-ui-plugin-manager`（v0.2.1-rc.2）。
> 这一节推翻了本文此前若干推断，**实现前必须以此为准重新讨论**。

### 15.1 官方的安装链路不是「裸 pnpm」

官方 `dsh plugin` CLI 与 Web 插件页**共用同一套 `operations.ts`**（`@deepseek-ai/dsh-plugin-manager`），CLI 只是它的一个入口。官方在一次安装中会做：

1. **inspect + registry 计划**：`pnpm view` 查询，按 `registry` → `fallbackRegistries`（默认 npmmirror）依次询问，私有源不落公共源；
2. **版本兼容性检查（pnpm 运行前）**：`engines.dsh` + `@deepseek-ai/dsh*` peer 依赖；不满足则**不下载任何东西**直接失败；豁免存 profile 的 `compatibility.json`（CLI：`version-exemptions` / `allow-version` / `revoke-version`）；
3. **快照与恢复**：pnpm 运行前快照 `package.json` + `pnpm-lock.yaml`；**失败或取消时恢复这两份文件**（pnpm 已下载文件可能保留；`pnpm-workspace.yaml` 有意不恢复以保留构建授权）；
4. **profile 写锁**：CLI 与 service 共用 manifest 写锁（`lockWaitMs` 默认 120s），串行化并发操作；
5. **存活与进程树**：service 运行若 `idleTimeoutMs`（默认 600000）内无任何捕获输出即被终止，报告 `timedOut`，**终止整棵进程树并等待其消失**（因为生命周期脚本可能比 pnpm 活得久）；每次运行记录在 `.plugin-manager/run.json`，结束删除；发现残留记录最多等 5 秒，否则不运行 pnpm 并报诊断；
6. **取消语义**：`cancelInstall(requestId)` 停止运行，**只在 pnpm 退出且文件恢复后**答复 `cancelled`；`applying` 阶段答复 `too-late`；其他 id 答复 `not-running`。CLI 继承终端，取消由操作者中断（Ctrl-C），不走 requestId；
7. **事件与日志**：`plugin-manager/install-log` 流式输出、`install-state`（installing / cancelling / applying）、`waitForInstall` 恢复丢失响应；完整日志在 `.plugin-manager/logs/operation-*/pnpm.log`（本机已存在该目录），返回体只带 `outputBytes`（默认 16 KiB）；
8. **构建脚本审批**：pnpm 11 拦截依赖脚本时失败并列出 `pendingBuilds`，Web 提供「允许这些脚本并重试」，授权写 `pnpm-workspace.yaml`。

### 15.2 官方的分类语义

- **`official` = 安装随附的可选组合包 / 按需条目**（`OPTIONAL_BUNDLES`），**与安装状态无关，也不等于 npm scope**；
- `installed` = profile 是否声明该依赖；`availability` = 随安装提供 / profile 包 / missing；
- UI 标签：「已安装」「有新版本」「随 DSH 提供」「实验性」；官方包以 `@deepseek-ai/dsh-experimental-` 前缀显示实验性标记；
- 官方列表来自 Host 的 `listBundles`（组合包选择、行、存活状态、错误），不是直接读 `package.json`。

### 15.3 我们的 B1 与官方的差异

| 维度 | 官方 | B1 现状 | 结论 |
| :--- | :--- | :--- | :--- |
| 安装入口 | `dsh plugin` / Web 共用 operations | 调 `dsh plugin` CLI | ✅ 一致（不是裸 pnpm） |
| 兼容性检查 | pnpm 前阻断 + 结构化拒绝码 | 由 CLI 间接执行，但**不展示**结构化诊断 | ⚠️ 部分一致 |
| 快照恢复 | 失败/取消自动恢复 manifest+lock | 依赖 CLI 内部逻辑；**外部强杀可能绕过恢复** | ❌ 冲突（见 15.4） |
| 并发 | profile 写锁 | UI 单面板 busy；多实例无约束（CLI 锁兜底） | ⚠️ 基本可用 |
| 取消 | `cancelInstall(requestId)`，有状态机 | 无取消 API | ❌ 不一致 |
| 超时/进程树 | idle 600s + 杀树 + run.json 守护 | 总时长 300s + 只 `child.kill()` | ❌ 不一致且更危险 |
| 日志 | `.plugin-manager/logs/**` | 仅内存输出面板 | ⚠️ 可复用官方日志 |
| 列表/分类 | listBundles：official/installed/availability/error/meta | 读 package.json + scope 猜「官方/第三方」 | ❌ 语义不一致 |
| 构建脚本审批 / 版本豁免 / 更新检测 | 有 | 无 | ❌ 差距 |
| 权限语义 | 管理操作需 full access 或逐次批准 | 用户在日常 GUI 中主动点击 | ⚠️ 需明确说明 |

### 15.4 关键后果：**外部「强杀式取消」与官方语义冲突**

官方保证「失败/取消后恢复 `package.json` + `pnpm-lock.yaml`」，这个恢复动作发生在 **dsh CLI 进程内部**。如果我们从外部 `kill_tree`：

- CLI 来不及执行恢复 → **manifest/lock 可能停在半改状态**；
- 留下 `.plugin-manager/run.json` → 下一次官方操作会等待 5s 后报「残留运行」诊断；
- 因此我们之前规划的「`jobobj` + `kill_tree` 取消」**不是更安全，而是破坏官方保证**。

正确的取消方向（按可行性排序）：

1. **首选：走 dsh 侧插件调用 `pluginManager.cancelInstall`**（即双向桥 B2/B3 的方向）——官方语义、官方状态机、官方恢复；
2. **次选：验证 `dsh plugin` CLI 对终端的 Ctrl-C 是否同样触发恢复**；若可以，用「请求中断 + 等待 CLI 自行退出/恢复」而不是外部杀树（Windows 下给子进程发 Ctrl-C 需 `GenerateConsoleCtrlEvent` + 共享控制台，需实验验证）；
3. **兜底：不做外部取消**，只展示进度与官方日志；超时交给官方 `idleTimeoutMs`；退出由用户关闭管理器（但需处理「CLI 仍在跑」的提示）；
4. 若不得已外部终止：必须把终态标为 `Unknown/可能未恢复`，并提示「运行 `dsh plugin --profile <p> install` 修复」，且要处理 `run.json`。

| P0 进程树治理 | 仍需要，但目的改为「与官方 idleTimeout/杀树对齐、防止残留」，**不是**实现取消 |

### 15.6 新增的开放问题（比原问题更根本）

1. **B1 的定位**：官方 Web 插件页已是完整实现（安装/取消/更新/审批/兼容性）。multiver 插件面板应：
   - (a) 只做「不启动 dsh 时的轻量入口 + 打开官方插件页」；
   - (b) 继续做薄壳，但只复用官方 CLI 语义并展示官方日志；
   - (c) 通过双向桥 B2/B3 深度集成官方 service（能拿到 cancelInstall/listBundles）。
2. **取消是否值得做**：如果 (a)/(b)，外部取消收益低、风险高，建议不做；如果 (c)，取消几乎免费（官方 API）。
3. **是否需要展示「随 DSH 提供」等官方标签**：需要 `listBundles`，外部 CLI 拿不到 → 可能需要 B2/B3，或接受 B1 只显示「已安装依赖 + profile bundles」。

> 结论：**B1 的插件安装底层与官方一致（同 CLI/operations），但我们的取消/分类/日志方案与官方语义不一致；取消设计应重新以「接入官方 service」为首选，而不是外部强杀。**

## 16. 第四条路：CLI-only 薄壳（2026-10-21 讨论）

**定义**：在 multiver 内把安装 / 取消 / 更新 / 审批 / 兼容性的交互都做完整，但底层**只调用 `dsh plugin` CLI**——不接 dsh service，也不做 dsh 侧插件。

### 16.1 源码依据（v0.2.1-rc.2）

- CLI 与 service **共用** `runPluginCommand` / `runProfilePnpm`（`@deepseek-ai/dsh-plugin-manager`）；唯一区别是 `execution`：
  - `cli`：stdio **继承**、`killDescendants: false`、无 idle timeout；
  - `service`：pipe 捕获、`killDescendants: true`、`idleTimeoutMs` 上界。
- CLI 的 plugin 命令（`@deepseek-ai/dsh/lib/plugin-*.js`）**没有 SIGINT/SIGTERM 处理器**（`dsh/lib` 里只有 `profile-boot` 为启动应用注册信号）；
- 取消只在 service 内以 `requestId` + `AbortController` 暴露（`cancelInstall`），CLI 没有对应入口；
- 快照恢复（`package.json` + `pnpm-lock.yaml`）在 operation 的进程内 `finally` 路径执行——**外部杀死进程不会执行**；
- CLI 每次运行会创建 `.plugin-manager/logs/operation-*/pnpm.log`；但 CLI 模式下 pnpm 输出继承终端，日志主要记录 dsh 自己的诊断，**完整输出靠调用方管道捕获**；
- CLI 已内建：兼容性预检（`engines.dsh` + peer）、registry 计划与回退、profile 写锁、`run.json` 互斥、失败/兼容性拒绝后的快照恢复与修复安装、`version-exemptions` / `allow-version` / `revoke-version` 子命令（`version-exemptions` 输出 JSON）。

### 16.2 能力矩阵

| 能力 | 第四条路可实现？ | 做法与边界 |
| :--- | :--- | :--- |
| 安装 | ✅ | 直接 `add <spec>`；官方兼容性预检/registry 回退/快照恢复全部由 CLI 保证 |
| 卸载 | ✅ | `remove <pkg>`；同样有恢复与锁 |
| 更新 | ✅（近似） | 先查 registry（`view`）判断新版本 → `remove` + `add <name>@<ver>`；**没有**官方「随 DSH 提供目标」语义 |
| 审批（构建脚本） | ⚠️ 需自实现 | CLI 只提示「把 allowBuilds 写进 `pnpm-workspace.yaml` 再重跑」；面板需自己解析 pnpm 输出、写 YAML、重试（官方这份逻辑在 service 里） |
| 兼容性 | ✅ | 安装时由 CLI 强制；豁免用 CLI 子命令（`version-exemptions` JSON）驱动 UI；拒绝详情需解析 stderr 文本 |
| **取消** | ❌ **不可** | 无 requestId / cancel 子命令；SIGINT 无 handler；外部 kill 会跳过快照恢复并留下 `run.json` |
| 列表/标签 | ⚠️ 受限 | 只能读 profile `package.json` + `dsh.profile.bundles`；拿不到官方 `listBundles` 的 official/availability/error/update 状态 |
| 日志 | ⚠️ 部分 | 官方 `pnpm.log` 在 CLI 模式下信息有限；主日志是我们自己捕获的管道输出 |
| 并发 | ✅ | CLI 自带 profile 写锁（`lockWaitMs` 120s） |
| 进度 | ✅ | 解析 CLI/pnpm 的 stdout/stderr 行 |

### 16.3 三种变体

- **4a（安全优先）**：其他能力全做，**取消不做**；UI 诚实说明“安装由官方 CLI 执行，取消需等其自身结束”。完全复用官方语义，零破坏。
- **4b（4a + 上游诉求）**：实现 4a，同时向 dsh 提 feature request：给 `dsh plugin` 增加优雅中断（SIGINT handler）或 `cancel` 子命令；在此之前不提供取消。
- **4c（4a + 最小 dsh 侧桥）**：只在需要取消时引入 dsh 侧能力（service `cancelInstall` 或本地 RPC）；属于 B2/B3 的缩小版，需先解决“helper 自己也要安装”的递归问题。

### 16.4 结论与建议

**第四条路成立**：安装 / 卸载 / 更新 / 审批 / 兼容性都能在“只用官方 CLI”的前提下做到完整（审批需自己写 allowBuilds），并发/日志/兼容性也都有官方兜底；**唯一硬缺口是取消**——这不是实现选择问题，而是官方 CLI 当前没有暴露取消语义。

建议：**走 4a/4b**——先做 CLI-only 薄壳，把取消明确标为“官方 CLI 不支持”，在文档与 UI 里如实说明；同时评估 4b 的上游诉求。仅当“取消”是硬需求时，才进入 4c（dsh 侧桥）。

### 16.6 决策记录（2026-10-21）

> **取消：挂起，不实现。** 原则：**官方不做，multiver 也不做**；等官方 CLI/service 提供可用的取消通道后再跟进。
> 因此本文的 P0/P1/P2 计划中与「取消」相关的部分全部冻结；下面只保留作为将来跟进的设计参考。
>
> **当前实现与官方对齐的范围（本轮已做）**：
> - 标签语义：去掉「官方/第三方（npm scope 猜测）」，改为「随 DSH 提供 / 已安装」；
> - 失败提示：识别官方 CLI 的 `allow-version` / `pnpm was not found` / `diagnostics: <logPath>` 并转成本地化提示；
> - 安装/卸载仍走官方 CLI（兼容性检查、快照恢复由官方保证）。
>
> **仍分歧、需后续「信息查询 + 桥接适配」解决**：
> - 官方 `listBundles` 的 `official / availability / error / 更新状态` 外部 CLI 拿不到；
> - 官方 `pendingBuilds`（构建脚本审批）只在 service 侧，CLI 只能提示用户手写 allowBuilds；
> - 官方 `version-exemptions` 可通过 CLI 子命令读/写，可作为下一步兼容性 UI 的数据源。

### 16.5 实现前需要验证的实验
