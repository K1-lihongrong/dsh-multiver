## 一、为什么先做这一轮

v0.3.7 已完成事件桥安全加固与契约测试。当前基线：Rust 单测 **202 passed / 1 ignored**；staged 4 passed；契约测试 4 passed / 1 ignored；CI 主流程通过。

v0.4.0 的实例模型会同时动版本、home、进程 key、窗口 label、配置和命令状态。直接做 UI/CLI 会反复返工。alpha.1 先固定**类型、配置和状态所有权**，不增加用户功能。

## 二、目标与边界

### 2.1 必须达成

1. 领域类型：`VersionId` / `InstanceId` / `HomeRef` / `ProcKey` / `LaunchTicket` 进入生产路径。
2. 配置可迁移：新增 `schema_version` 与实例表；旧 `isolated_versions` 自动迁移，行为不变。
3. 状态单一所有：`AppCtx` 收敛 `procs` / `intent` / `dirs` / `scan_cancel`；55 个命令迁移到 `State<'_, AppCtx>`。
4. 外部依赖有端口：pnpm、dsh 启动、文件系统、时钟建立 trait 边界。
5. 旧行为不回归：202 个既有单测断言不删、不弱化。

### 2.2 明确不做

- ❌ 不做实例 CRUD / 挂载的 GUI 或 CLI 用户功能（属 v0.4.0）
- ❌ 不做 `dsh_adapter`、`JobRegistry`、`tauri-specta`（属 alpha.2）
- ❌ 不改插件安装/卸载/目录模型；只补「更新事务 + 批量更新」这一条用户可见路径
- ❌ 不拆多 crate 工作区，不打 GitHub Release

### W5 插件批量更新与失败回滚（4–5 人日）

现状：已安装页能手动检查单个版本/profile 的更新，但只能逐项点「更新」；更新是前端连续调 `remove` + `add`，若 add 失败，插件会停留在已卸载状态。

| # | 任务 | 交付 | 人日 |
| :-- | :--- | :--- | ---: |
| U1 | 更新事务模型 | `PluginUpdatePlan`：记录包名、当前版本、原依赖 spec、目标版本；单插件 `remove → add → verify` | 1 |
| U2 | 失败回滚 | add 失败时用原 spec 重装并校验；回滚失败返回明确错误与人工恢复命令 | 1 |
| U3 | 批量更新命令 | `ds_plugin_update_batch` 顺序执行，逐项发 `plugin-update-progress`；单项失败只回滚该项并继续 | 0.5–1 |
| U4 | 前端批量入口 | 「全部更新」按钮、确认框、进度列表、成功/失败汇总；保留单插件更新 | 1 |
| U5 | 测试 | fake runner 覆盖 remove 失败 / add 失败 / 回滚成功 / 回滚失败；真实 profile 手工冒烟 | 0.5–1 |

**事务语义**

- 单项更新是一个事务：先记原依赖 spec，再 remove，再 add 目标版本，最后读 package.json 校验。
- add 失败 → 用原 spec 回滚；回滚成功则该项标记失败但插件仍可用。
- 回滚失败 → 返回原错误 + 回滚错误 + 手动恢复命令，前端高亮提示，不静默吞掉。
- 批量更新逐项事务：已成功项保留，失败项独立回滚，不在批次级整体回滚；结果必须列出每项状态。
- 更新目标遵守官方语义（remove → add），不改成直接 `pnpm update`，避免破坏 dsh profile 的依赖约束。

**边界**

- 本轮只批量更新「当前版本 + 当前 profile」检测到的可更新项；跨版本聚合留到后续。
- 官方随附 bundle 不进入批量更新；锁定项在预检阶段直接排除并说明原因。
- 不改变插件安装/卸载的权限模型和命令名。

**验收**

- 批量选择 N 个插件后按顺序执行，进度显示 `i/N + 包名 + 阶段`。
- 人为让某个 add 失败，该项自动回到原版本，其余项继续，结果汇总正确。
- 回滚失败时日志与 UI 都给出可执行的人工恢复命令。
- 单插件更新路径回归通过；真实 pnpm/dsh profile 冒烟通过。

## 六、风险与回滚

| 风险 | 缓解 |
| :--- | :--- |
| newtype 改造面大 | 每改完一个模块跑 `cargo check`；不保留 String 临时桥 |
| 迁移中断产生幽灵实例 | `state=deleting` + 启动扫描续完；迁移前备份原 config |
| 迁移错误覆盖旧文件 | 完整成功后才原子替换；失败保留原文件并写日志 |
| AppCtx 切换引发窗口时序问题 | 保留 generation 语义；两窗口并行冒烟；按模块分批提交 |
| 端口抽象改坏安装 | adapter 先包现有实现；fake 对拍后再迁移 |
| 更新时 remove 成功、add 失败 | 单插件事务：按原依赖 spec 重装；回滚失败返回人工恢复命令 |
| 批量部分成功造成状态不清 | 逐项结果汇总为 updated / failed / rollback_failed，前端明确展示 |
| 更新目标版本与 profile 约束冲突 | 预检 `outdated` 结果 + 目标版本格式；失败走单项回滚 |
| 周期膨胀 | 每工作包独立 PR；W4 超期则暂缓 Fs/Clock 扩展 |

回滚：任一工作包失败回滚对应 PR；迁移失败保留原 `config.json` 与旧 home；alpha.1 不发布 Release，tag 只作回滚锚点。
