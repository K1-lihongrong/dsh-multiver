## 关于两个「dsh 自身缺陷」

`0.1.5-rc.1` 与 `0.1.2-rc.1` 启动时报：

```
Error: dsh: user patch-layer watching requires the Cordis HMR service
    at watchUserPatches (.../dsh-app-boot/lib/index.js)
```

**与插件无关**，依据：

1. **对照组**：用全新空 `DSH_HOME`（不含任何插件）启动 `0.1.5-rc.1`，同样报此错、同样无法监听端口。
2. **模板自带矛盾**：该版本自己生成的 profile 模板写了 `"patchReload": "live"`，但它自身没有提供 HMR 服务——模板要求了运行时不存在的能力。
3. **手工去掉 `patchReload` 后仍失败**，说明触发点在别处（可能 `cordis.patch.yml` 的存在本身）。
4. 高版本（`0.1.5-rc.3` 起）不再有该字段，启动正常。

结论：这是 dsh 0.1.5-rc.1 及更早版本的自身缺陷，与本插件无关。这些版本无法作为「支持/不支持」的判定依据。

## 关于 0.1.3-alpha.2 安装失败

`pnpm add` 时 `fs-ext@2.1.1` 编译失败：

```
gyp ERR! not ok
[ELIFECYCLE] Command failed with exit code 1.
```

`fs-ext` 是原生模块，需要 C++ 编译工具链。本机装有 VS 2022 与 Python 3.12，仍未通过。

这不是插件问题——是 dsh 该版本依赖了需要现场编译的原生模块。multiver 的安装参数已带 `--config.dangerouslyAllowAllBuilds=true`，说明构建脚本是放行的，失败发生在编译阶段本身。

## 复现方法

```powershell
# 1. 为某版本准备独立 home
$v = 'E:\.LLM-AGENTS\deepseek-harness\versions\<版本>'
$h = "$env:TEMP\compat-<版本>"
$env:DSH_HOME = $h

# 2. 装插件
& "$v\node_modules\.bin\dsh.CMD" plugin --profile web add <插件 tgz 路径>

# 3. 启动
& "$v\node_modules\.bin\dsh.CMD" web --port 3097 --no-open

# 4. 验端点（带 token 调 state；不带 token 应 401；GET 应 405）
```

## 测试纪律

- 每轮测试前快照真实数据根的 `config.json`（SHA256），测完核对未变
- 测试用的 `DSH_HOME` 全部位于 `%TEMP%`，测完移入回收站
- 临时安装的 dsh 版本用 `uninstall` 清理，不留 `broken_versions` 标记
